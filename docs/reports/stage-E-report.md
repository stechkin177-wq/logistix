## Что сделано

**E1. R-1** (`apps/finance/income.py`). Доход признаётся только при одновременном выполнении: (а) для каждого действующего груза заказа покрыты все отрезки маршрута неотменёнными участками действующих рейсов (`route_coverage(..., legs=...)`); (б) все действующие рейсы завершены (`completed_status` + `completed_at`); (в) последняя остановка каждого груза выполнена (`done`) ИЛИ участок, заканчивающийся на ней (или прежний участок без остановок), завершён - для двухточечных грузов это то же завершение рейса, прежнее поведение сохранено. Один предикат служит признанию (`recognize_order_income`), возврату (`unrecognize_order_income`) и правилу переключения (`switching.apply_cutover_rule`). Причины отказа (`blockers`): `no_active_trips`, `trips_not_completed`, `route_not_assigned`, `not_delivered`, `in_storage`, `no_consignments`. Дата признания - максимум из дат завершения рейсов и `done_at` последних остановок (в часовом поясе компании). Идемпотентность и атомарность как в G1 (блокировки Order -> Trip -> Income, ошибка хука откатывает основную операцию). Хуки: `create_trip` (раньше хука не было), `reassign`, `change_trip_status` (в т.ч. отмена), `record_event`, подтверждение и сторно передачи, удаление/восстановление рейса.

**E2. Метод распределения.** `Expense.allocation_method` (equal по умолчанию | proportional | manual), CHECK в БД; миграция finance.0011 (аддитивна, обратима, самодостаточна): `source=migrated` -> `manual`, прочие `equal`; `migrate_finance` создаёт перенесённые расходы сразу `manual`. Пропорционально (`proportional_rows`): вес (доля участка, а при пустой доле - вес груза), если весов нет - объём, затем паллеты, иначе поровну; наибольший остаток (`split_proportionally`, копейки по G1); сумма долей = сумме расхода при `requires_full_allocation`. Сервисы: `create_carrier_expense(allocation_method=...)` (явные доли = manual, другой метод с долями - ошибка), `reallocate(expense, method)` (в одной транзакции под блокировкой заказов, рейса и расхода, с проверкой периода и аудитом), `set_allocations` -> manual, `sync_trip_expense` сохраняет метод (proportional - пересчёт по весам; equal - поровну между теми же заказами, только если прежние доли действительно были «поровну», иначе прежняя пропорциональная корректировка; manual - прежние пропорции). Двойной учёт исключён: доля - одна строка (заказ, рейс) с уникальностью, сумма по заказам = сумме по рейсам = сумме расхода. API: `allocation_method` в ответе расхода, параметр `allocation_method` в `POST /api/finance/trips/{id}/carrier-expense/`, `POST /api/finance/expenses/{id}/reallocate/` (`finance.update`). Frontend: выбор метода в панели долей расхода.

**E3. Хуки удаления и смены валюты (только `engine=new`).** Рейс с активным расходом `carrier_transport` -> 409 `trip_has_expense`; заказ с признанным доходом, активными долями расходов или активными (не отменёнными) счетами -> 409 `order_has_finance` (транзакция откатывается целиком); плановые доходы заказа без счетов аннулируются (`void_income`) в той же транзакции; восстановление заказа создаёт плановый доход заново и пересчитывает признание; восстановление рейса проверяет конфликты участков (409 с пояснением) и пересчитывает признание; смена валюты рейса при активном расходе -> 409 `trip_currency_locked`. Удаление рейса пересчитывает покрытие маршрута, местонахождение грузов и признание (период и права - как в прочих пересчётах).

**E4. **E5. Сверка на данных с участками** (`test_stage_e_reconcile.py`): `migrate_finance` и `reconcile_finance` на заказе с многоточечным маршрутом, двумя рейсами двух перевозчиков, передачей на склад и строками расхода по рейсам - `success`, `unexplained == 0`, повтор миграции не меняет данные, сверка только читает; правило переключения использует R-1. ## Интерпретации и решения без явного указания в ТЗ (для подтверждения заказчиком)

1. **Изменены два прежних теста G1** (`test_income.py::test_cancelled_trip_is_not_counted`, `::test_unfinished_cancelled_waits_for_remaining`): заказ с двумя грузами, у одного из которых единственный рейс отменён. По G1 доход признавался после завершения оставшегося рейса; по R-1 (а) и addendum разд. 4 («отмена рейса снимает назначение участка и блокирует признание, пока не назначен новый рейс») такой груз не назначен - доход не признаётся до назначения нового рейса. Тесты обновлены: добавлен шаг «груз назначен на новый рейс -> признано». Остальные однозвенные сценарии G1 проходят без изменений. Если заказчик считает, что отменённый единственный рейс груза должен исключать груз из условия, правило надо уточнить.
2. **Завершение участка для (в):** участок считается завершённым, если его статус `done` ИЛИ его рейс завершён по `completed_status` компании (на случай, когда `completed_status` не имеет системного кода COMPLETED).
3. **Груз без маршрута (меньше двух остановок):** для (а) достаточно любого действующего участка, для (в) - завершённого участка. Последняя остановка в статусе `skipped` выполненной не считается.
4. **Вес заказа в рейсе для пропорционального метода:** по каждому грузу берётся наибольшее значение по его неотменённым участкам этого рейса (доля участка, а при пустой доле - количество груза), затем суммируется по грузам заказа (груз на двух участках одного рейса считается один раз). Заказ с нулевой долей по выбранному измерению доли расхода не получает.
5. **`equal` у существующих расходов** - значение по умолчанию; при синхронизации цены доли выравниваются поровну только если до этого были «поровну», иначе сохраняются прежние пропорции (чтобы не потерять ручное распределение, сделанное до этапа).
6. **Удаление рейса при признанном доходе заказа** не блокируется (в списке E3 нет такого пункта): признание пересчитывается обычным способом (возврат в planned через период/права), блокируется только рейс с активным расходом.
7. **Удаление заказа:** плановые услуги (kind=service) без счетов тоже аннулируются; при восстановлении аннулированные услуги не возвращаются, создаётся только новый плановый доход перевозки. «Активные счета» - не отменённые (черновик и выставленный).
8. **Блокировка валюты рейса** действует только при активном расходе `carrier_transport` (расходы `other` валюту рейса не используют).
9. **Хук после `create_trip`** добавлен (раньше создание рейса пересчёт не вызывало): новый незавершённый рейс заказа теперь может вернуть ранее признанный доход (по общему правилу возврата).
10. **Проверка восстановления рейса на конфликты участков** действует только при `engine=new` (для legacy поведение не меняется).

## Оговорки

- Задание на этап E требует «все прежние тесты apps/finance проходят»: проходят все, кроме двух, обновлённых по интерпретации 1.
