## Что сделано

**C1. Схема и миграции.** `TripConsignment`: `from_stop`/`to_stop` (FK на `ConsignmentPoint`, null, PROTECT, related_name `legs_from`/`legs_to`), `leg_seq` (smallint, 1), `status` (planned/in_progress/done/cancelled, planned), доли `weight_kg`/`volume_m3`/`pallets` (NULL = весь груз). Старая уникальность (рейс, груз) заменена: unique(рейс, груз, from_stop, to_stop) и частичная unique(рейс, груз) WHERE from_stop IS NULL AND to_stop IS NULL (в БД это уникальный индекс); CHECK «обе остановки заданы или обе пусты»; CHECK статуса и долей; индекс (consignment) сохранён. Миграции: 0011 схема, 0012 данные: `from_stop` - первая погрузка груза, `to_stop` - последняя выгрузка (нет такой пары или from.seq >= to.seq - NULL, NULL), статус по системному КОДУ статуса рейса (COMPLETED -> done, CANCELLED -> cancelled, иначе planned), идемпотентно, с учётом RLS, без импорта кода приложения. Откат 0011 допустим, пока нет двух участков одного груза в одном рейсе (иначе остановка с ошибкой, данные не удаляются).

**C2. Правила (сервис `trips/legs.py`).** `from_stop.seq < to_stop.seq`, обе остановки принадлежат ЭТОМУ грузу; доли >= 0 и не больше количества груза; на каждом отрезке маршрута (между соседними остановками) сумма указанных долей неотменённых участков (рейс не удалён) по каждому измерению не больше количества груза; участок с пустыми долями по всем измерениям («весь груз») исключает другие участки на том же отрезке; один груз на двух рейсах на разных отрезках (передача) допустим; участок можно сузить/расширить через `reassign(legs=...)`. **Покрытие** `route_coverage(consignment)` без фиктивных строк: отрезки между соседними остановками (`from_stop, to_stop, from_seq, to_seq, covered, legs, trips[{id, number, status}]`), список непокрытых `uncovered`, признак `fully_assigned`; покрыт отрезок, если есть неотменённый участок не удалённого рейса с `from.seq <= начало` и `to.seq >= конец`. Добавлено в API груза и заказа: `route: {stops, coverage}`.

**C3. Сервисы рейса.** `create_trip(consignment_ids, carrier_id, data, user, *, legs=None, ip=None)` и `reassign(trip, consignment_ids, user, *, legs=None, ip=None)`: `consignment_ids` - весь маршрут (участок от первой погрузки до последней выгрузки), `legs` - дополнительно `[{consignment, from_stop, to_stop, shares}]`; грузы участков добавляются к набору; для груза с явными участками «весь маршрут» не создаётся. `is_consolidated` пересчитывается по заказам участков, номер рейса не меняется, порядок блокировок прежний (рейс -> заказ -> грузы по возрастанию pk; проверки участков идут под блокировкой строк грузов), аудит `consignments` и `legs`. Статус рейса синхронизирует статусы участков (`sync_leg_statuses`): завершён -> done, отмена -> cancelled (снимает покрытие), в пути/выгрузка -> in_progress, иначе planned; возврат рейса из отмены проверяет пересечения с участками, назначенными за время отмены. API рейса: `legs` в ответе (груз, заказ, откуда/куда, `leg_seq`, статус, доли), `consignments`/`orders` без изменений (груз с несколькими участками в рейсе показан один раз), `legs` в запросе создания и `reassign`; PATCH с `legs` - 400. Финансы: запросы `active_trips`, `trip_order_ids`, `_order_ids_of_trip` используют `pk__in`/множества, поэтому несколько участков одного груза в одном рейсе не дают дублей; тест подтверждает один доход и одну строку `IncomeTrip`. Документы: в контекст рейса добавлен `trip.legs[]`.

**C4. Frontend.** Карточка рейса: список участков (груз, откуда - куда, доли или «весь груз», статус). ## Интерпретации и решения без явного указания в ТЗ

1. **Прежний путь `consignment_ids` остаётся «разрешающим».** Перегруз «один груз в нескольких рейсах на весь маршрут» существовал до этапа (тесты G1/forwarding и данные миграций), поэтому участок «весь груз на весь маршрут», созданный через `consignment_ids`, по-прежнему может сосуществовать с таким же участком другого рейса. Правило «весь груз исключает другие рейсы на отрезке» строго применяется к явным `legs` и к любому сочетанию, где участвует участок с долей/частью маршрута (в том числе против прежних «весь маршрут» других рейсов). Иначе пришлось бы ломать существующих клиентов и данные.
2. **Пустая доля по одному измерению** не ограничивает это измерение (параллельные доли можно задавать, например, только по весу); «весь груз» - когда пусты ВСЕ три доли.
3. **`leg_seq`** - номер участка внутри пары (рейс, груз) по порядку маршрута (при единственном участке - 1).
4. **Покрытие** считает наличие неотменённого участка не удалённого рейса, доли не учитываются (частично покрытый долями отрезок считается покрытым). Груз без маршрута (< 2 остановок): `segments = []`, `fully_assigned = false`. Запись без остановок (NULL, NULL) считается покрывающей весь маршрут.
5. **Статусы участков** жёстко следуют за статусом рейса по системному коду (отдельного ручного отказа от одного участка нет). Возврат рейса из CANCELLED проверяет конфликты (иначе 400).
6. **PROTECT остановки** действует и для участков отменённых рейсов (запись участка остаётся в истории); восстановление рейса из корзины пересечения участков не проверяет.
7. **Права/модули**: ничего нового не вводилось; `legs` в запросах требуют тех же прав, что создание/`reassign` рейса. Явные `shares` в `create` игнорируют лишние ключи.
8. **Аудит**: `legs` пишется только если участки передавались явно.
9. **`trips_count` груза** считает рейсы, а не участки (иначе груз с двумя участками в одном рейсе считался бы дважды).
10. **Документы**: помимо `stops[]` (этап B4) добавлено `trip.legs[]` (критический тест «ключи stops/legs»).
11. **Границы числа запросов**: список рейсов +1 запрос (участки), список заказов +1 запрос (участки для покрытия); число запросов по-прежнему не зависит от числа записей (тесты с «плоским» числом запросов обновлены на единицу).
