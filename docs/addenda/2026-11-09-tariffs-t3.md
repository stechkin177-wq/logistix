# Тарифная система, этап T3: лимиты

Решение заказчика (2026-11-09): название и логотип компании - базовая возможность всех тарифов
(не ограничиваются); `white_label` - расширенное брендирование платформы (убрать упоминания
LogistiX и т.п.), `custom_domain` - отдельная функция. Привязка этих функций к операциям - отдельным
шагом при реализации расширенного брендирования; на изменение названия и логотипа функции не влияют.

## Что реализовано
- Лимиты - данные тарифа: `Plan.limits` = `{код: целое >= 0 | null}`. Администратор меняет их через
  `PATCH /api/platform/plans/{code}/` (поле `limits`, при создании тоже). Нет ключа или `null` -
  без ограничений; `0` - создавать нельзя. Конкретные значения и их число в коде не заданы.
- Каталог измеряемых величин (`apps/billing/limits.py`): что считается (модель, фильтр, всего или за
  календарный месяц компании). Типы: сотрудники, техника, водители, клиенты, перевозчики, заказы в
  месяц, рейсы в месяц, документы в месяц; `max_ocr_per_month` объявлен, но пока не измеряется
  (модуля нет, ограничение не применяется). Новый тип ограничения - одна запись каталога.
  Справочник для панели: `GET /api/platform/catalog/` (поле `limits`).
- Серверная проверка при создании записи (сигнал `pre_save`) для ЛЮБОГО пути создания (API,
  сервисы, ORM). Внутри транзакции строка компании блокируется: два одновременных запроса не
  пройдут оба. Ответ `402 limit_exceeded` с `limit_code`, `limit`, `usage`. Нет подписки -
  проверка пропускается (доступ закрывает шлюз подписки). `bulk_create` лимитом не проверяется.
- Понижение тарифа: данные не удаляются; при использовании выше нового лимита блокируется только
  создание новых объектов, существующие читаются и правятся. Повышение: лимит читается из тарифа
  в момент проверки, поэтому ограничение снимается автоматически.
- `GET /api/billing/usage/`: по каждому типу лимит, использование и признак превышения (для
  интерфейса и предупреждений).
- Прежние явные проверки техники и водителей заменены общей; лимит сотрудников использует тот же
  механизм (активация сотрудника тоже учитывается).

## Совместимость options -> features
Интерфейс платформы `plan.options` не использует (читает только код и название тарифа). Для
внешних клиентов публичные ответы тарифов (`/api/billing/plans/`, `/api/billing/subscription/`)
сохраняют устаревшее поле `options` (только чтение, `white_label` и `custom_domain` выводятся из
`features`); новый клиент использует `features`. Поле будет удалено отдельным решением.

## Важно
- Значения лимитов тарифа «Старт» (сотрудники 5, техника 5, заказы 200 в месяц) теперь реально
  применяются ко всем перечисленным созданиям; ранее проверялись только сотрудники и техника.
  Значения предварительные, администратор меняет их без кода.
