# 2. Модули без искусственных зависимостей

## 2.1. Принцип зависимостей
Жёсткая зависимость (`requires`) допускается **только** там, где модуль технически не может работать без другого (обязательная ссылка в данных или обязательный API). Всё, что лишь расширяет возможности, — мягкая связь (`enhances`): модуль работает без неё, а функции этой связи появляются автоматически при включении второго модуля. Каждая жёсткая зависимость в каталоге сопровождается обоснованием; список жёстких зависимостей пересматривается при добавлении модулей.

## 2.2. Обновлённый каталог (заменяет таблицу в разд. 2.2 v1.0)

| Модуль | Содержимое | `requires` (жёстко) | `enhances` (мягко) |
|---|---|---|---|
| `core` | компании, пользователи, роли, справочники, нумерация, аудит, корзина | — | — |
| `documents` | шаблоны, выдача и журнал документов, вложения, снимки | `core` | `forwarding`, `finance`, `fleet`, `drivers` |
| `forwarding` | клиенты, перевозчики, заказы, грузы, рейсы, участки, передачи | `core` | `documents`, `finance`, `fleet`, `drivers`, `gps` |
| `finance` | счета, оплаты, доходы, расходы, периоды, курсы | `core` и данные, на которые ссылается (заказы, рейсы) → `forwarding` | `documents` |
| `fleet` | техника, обслуживание, ремонт, страхование | `core` | `documents`, `drivers`, `forwarding`, `gps` |
| `drivers` | водители, документы, назначения | `core` | `documents`, `fleet`, `forwarding` |
| `driver_app` | мобильный интерфейс водителя | `drivers`, `forwarding` (показывает рейсы) | `documents`, `ocr`, `gps` |
| `gps` | провайдеры, карта, геозоны | `fleet` (устройство привязывается к технике) | `forwarding`, `notifications` |
| `ocr` | распознавание документов | `documents` (обрабатывает вложения) | `finance`, `forwarding` |
| `notifications` | центр уведомлений, Telegram | `core` | любые модули-источники событий |
| `analytics` | отчёты, настраиваемый дашборд | `core` | `forwarding`, `finance`, `fleet`, `drivers` (виджеты появляются по доступным модулям) |

Изменения относительно v1.0: `documents` больше не требует `forwarding`; `drivers` не требует `fleet`; `analytics` требует только `core`; `finance` остаётся зависимым от `forwarding`, потому что его данные (доход, расход, счета) обязательно ссылаются на заказы и рейсы. Выделение рейсов из `forwarding` в отдельный модуль сейчас не вводится (все действующие эндпоинты рейсов остаются в `forwarding`); это отдельный вопрос на будущее, если появятся компании без заказов с собственными рейсами.

## 2.3. Архитектура документов без привязки к `forwarding`
Сейчас ядро документов знает о заказах, рейсах, счетах и клиентах (`documents/context.py`, поля `IssuedDocument.client/order/trip/invoice`). Для независимости:
1. **Универсальный субъект документа.** `IssuedDocument` и вложения получают пару `subject_type` (строка вида `forwarding.order`, `fleet.vehicle`, `drivers.driver`, `fleet.insurance`, `finance.invoice`, `finance.payment`, …) и `subject_id`. Прежние поля `client/order/trip/invoice` сохраняются для совместимости и заполняются как раньше; новые документы заполняют универсальную пару (и прежнее поле, если субъект из `forwarding`/`finance`).
2. **Реестр поставщиков документов.** Каждый модуль регистрирует «поставщика»: какие виды документов он поставляет, как строится контекст подстановки, какие права нужны для выдачи по субъекту. Ядро `documents` не импортирует модели других модулей; поставщики регистрируются при запуске, если модуль включён у компании.
3. **Виды документов принадлежат модулям.** Договор, заявка, договор-заявка перевозчику, акт, счёт на оплату, CMR, письмо остаются видами модулей `forwarding`/`finance`; для `fleet` и `drivers` поставщики добавляются в этапе 2 (например, акт обслуживания, приказ, справка). Вид доступен компании, только если включён его модуль и есть право.
4. **Вложения** (этап 3 ТЗ) используют ту же универсальную пару и работают для любых субъектов, включая водителей, технику, страхование, платежи.
5. Совместимость: действующие шаблоны, снимки и журнал выданных документов не меняются; метки `trip.price`, `trip.carrier_price` и прочие работают как раньше.

## 2.4. Остальные правила модулей (из v1.0, без изменений)
Три независимых уровня (тариф, конфигурация компании, права), итоговый доступ = тариф ∩ компания ∩ право; профили деятельности; включение только при выполнении `requires`; отключение блокируется зависимыми; данные не удаляются и возвращаются при повторном включении; право `company.manage_modules`; аудит; смена тарифа не теряет данные; **`finance` нельзя отключить при `engine ∈ {shadow, new}`**.
Дополнительно: `CompanyModule` хранит конфигурацию, `Company.modules` обновляется как проекция до отдельного решения о его удалении; существующим компаниям с `forwarding` миграция включает `finance` и `documents` (поведение не меняется).

# 3. Передачи груза (уточнение), участки, права

## 3.1. Передача `CargoTransfer`
Поля как в v1.0 с изменениями:
- `to_trip` **необязателен** (`null=True`); фиктивные рейсы не создаются;
- `from_trip` необязателен для передачи «со склада» (груз взят со склада, предыдущего рейса в этой записи нет);
- `transfer_kind`: `to_carrier` (другому перевозчику), `between_vehicles` (перегрузка между ТС), `to_storage` (на склад без назначенного следующего рейса), `from_storage` (со склада на новый рейс);
- `to_stop` — остановка вида `transfer` (склад/хаб) с фактическим статусом; пока `to_trip` пуст, остановка остаётся «груз на хранении» (`location_status = in_storage`);
- запись неизменяема; исправление — сторно новой записью; вложения (документы приёма-передачи) через механизм вложений.
Когда следующий рейс назначается, создаётся запись `from_storage` (с `to_trip`), а участок «склад → дальше» назначается на этот рейс. Пока такого участка нет, R-1 запрещает признание дохода.

## 3.2. Участок и права
- Участок реализуется развитием `TripConsignment`, перевозчик, водитель и техника берутся из рейса; индивидуальной подмены нет.
- Право `consignments.transfer` (подтверждение передачи): Администратор, Менеджер, Диспетчер. Водитель может **инициировать** запись (через `driver_app`), подтверждает уполномоченный сотрудник. Право `company.manage_modules`: Администратор.

# 4. Правило признания дохода R-1 (новая редакция Master Specification §6.3.1)

**Прежнее правило:** доход признаётся после завершения всех действующих рейсов заказа.
**Новая редакция:** доход заказа (`freight`) признаётся только при одновременном выполнении трёх условий:
1. для **каждого** груза заказа каждому необходимому участку маршрута назначен рейс (для однозвенного груза — единственный участок);
2. завершены **все действующие** рейсы заказа (не `CANCELLED`);
3. выполнены **последние остановки** всех грузов (груз доставлен: `location_status = delivered`).
Если следующий участок ещё не назначен, груз на хранении (`in_storage`) или не доставлен, доход не признаётся. Признание атомарно и идемпотентно (как в G1); дата признания — дата последнего события из условий (завершение последнего рейса или фиксация последней доставки). Для существующих однозвенных грузов без остановок фактические данные берутся из завершения рейса, поэтому прежнее поведение сохраняется. Отмена рейса снимает назначение участка и блокирует признание, пока не назначен новый рейс.

# 5. Распределение расходов (новая редакция Master Specification §6.5, дополнение)

- Методы распределения расхода рейса по заказам: `equal` (по умолчанию, поровну), `proportional` (пропорционально долям груза на участках рейса: по весу; если вес не задан — по объёму, затем по паллетам, иначе поровну), `manual` (ручные суммы).
- Метод сохраняется в расходе (`allocation_method`); смена метода пересчитывает доли в одной транзакции под блокировкой расхода, копейки распределяются по правилу G1.
- Сумма долей не превышает сумму расхода; для `requires_full_allocation` равна ей. Каждая доля учитывается один раз при любой группировке (по заказу, рейсу, позже по технике и водителю), поэтому двойного учёта нет.
- Автокоррекция при изменении `carrier_price` сохраняет выбранный метод (для `manual` — прежние пропорции).

# 9. Критерии приёмки (дополнения к разд. 8 v1.0)

**Модули и зависимости**
- Каждая жёсткая зависимость каталога обоснована; тест, что `documents` включается и работает без `forwarding` (выдача документа по субъекту водитель/техника/страхование/платёж через тестового поставщика; журнал, снимок, скачивание).
- Включение `forwarding` рядом с `documents` добавляет его виды документов без перенастройки; отключение `forwarding` не ломает журнал выданных документов других субъектов.
- `finance` нельзя отключить при `engine ∈ {shadow, new}`; при отключённом `finance` фоновые хуки движка работают.
- `Company.modules` совпадает с `CompanyModule` (проекция) при любых изменениях; чтение идёт из `CompanyModule`.

**Передачи**
- Передача на склад без `to_trip` создаётся без фиктивного рейса; `location_status = in_storage`; последующая запись `from_storage` с рейсом; журнал полный; сторно вместо правки.
- Водитель инициирует, уполномоченный подтверждает; без права `consignments.transfer` подтверждение запрещено.

**R-1 (финансы)**
- Заказ, чей второй участок не назначен: доход не признан даже при завершённом первом рейсе.
- Груз на складе (`in_storage`): доход не признан; после назначения рейса и доставки — признан один раз.
- Все участки назначены и последняя остановка выполнена, все рейсы завершены → доход признан на дату последнего события; повтор события не создаёт второй доход.
- Отмена рейса участка снимает назначение и блокирует признание; прежние однозвенные сценарии G1 проходят без изменений.

**Распределение расходов**
- Три метода: `equal` по умолчанию, `proportional` по долям груза (проверка копеек, нулевой веса/объёма, fallback), `manual`; сумма долей ≤ суммы расхода; сумма расхода учитывается один раз при любой группировке; смена метода и автокоррекция `carrier_price` сохраняют инварианты.

**Общее**
- Все миграции аддитивные и обратимые, RLS и изоляция проверены под `logistix_app` после каждой; существующие тесты проходят; итоговый полный прогон остаётся на конец плана.
