# 2. Модульная архитектура компании

## 2.1. Три независимых уровня управления
1. **Тариф** (`Plan.modules`): какие модули вообще доступны компании. Управляет владелец платформы.
2. **Конфигурация компании** (новая таблица `CompanyModule`): какие из доступных модулей включены у конкретной компании. Управляет владелец компании.
3. **Права сотрудников** (существующий RBAC): что внутри включённого модуля может делать каждый пользователь.

Итоговый доступ к функции = модуль есть в тарифе **И** включён компанией **И** у пользователя есть право. Ни один уровень не заменяет другой. Проверяется на сервере (расширение `ModuleRequired`), интерфейс только отражает.

## 2.2. Каталог модулей
Централизованный каталог (платформенная таблица `Module`, не принадлежит компании; наполняется миграцией и админ-панелью платформы):

| Поле | Смысл |
|---|---|
| `code` | неизменяемый код модуля |
| `name`, `description`, `sort` | отображение |
| `is_core` | основа, всегда включена и не отключается (компании, пользователи, роли, справочники, нумерация, аудит, корзина) |
| `requires` | жёсткие зависимости (список кодов) |
| `enhances` | мягкие зависимости (работает без них, но расширяет) |
| `sections` | какие разделы прав (`orders`, `trips`, `finance`, …) принадлежат модулю |
| `status` | `available` / `beta` / `retired` |

Предлагаемый начальный каталог (без новых функциональных обещаний, только структура существующего и запланированного):

| Модуль | Содержимое | `requires` |
|---|---|---|
| `core` | компании, пользователи, роли, справочники, нумерация, аудит, корзина | — |
| `forwarding` | клиенты, перевозчики, заказы, грузы, рейсы | `core` |
| `finance` | счета, оплаты, доходы, расходы, периоды, курсы | `forwarding` |
| `documents` | шаблоны, выдача, журнал документов | `forwarding` |
| `fleet` | техника, обслуживание, ремонт, страхование | `core` |
| `drivers` | водители, документы, назначения | `core` (`enhances`: `fleet`) |
| `driver_app` | мобильный интерфейс водителя | `drivers`, `forwarding` |
| `gps` | GPS-провайдеры, карта, геозоны | `fleet` |
| `ocr` | распознавание документов | `documents` |
| `notifications` | центр уведомлений, Telegram | `core` |
| `analytics` | отчёты и настраиваемый дашборд | `forwarding` (`enhances`: `finance`, `fleet`, `drivers`) |

## 2.3. Конфигурация компании и профили
- `CompanyModule` (tenant-таблица, RLS): `company`, `module_code`, `enabled`, `enabled_at/by`, `disabled_at/by`, `reason`. Уникальность `(company, module_code)`. Существующий `Company.modules` остаётся как проекция для совместимости на переходный период (запись в обе стороны, чтение из новой таблицы), удаляется только отдельным решением.
- **Профили деятельности** (`ActivityProfile`, платформенная таблица): рекомендуемые наборы модулей («экспедитор», «перевозчик», «экспедитор и перевозчик», …). Профиль предлагается при регистрации и в настройках, применяется как стартовый набор и далее правится вручную; профиль не ограничивает.
- Существующие компании: миграция создаёт `CompanyModule` по текущему `Company.modules`; компаниям с `forwarding` включаются `finance` и `documents` (сейчас они доступны внутри `forwarding`), чтобы поведение не изменилось.

## 2.4. Правила включения и отключения
- Включить можно только модуль, доступный по тарифу, у которого включены все `requires`.
- Отключить нельзя модуль, от которого зависят включённые модули (сообщение со списком зависимых; каскад только по явному подтверждению).
- **Данные не удаляются и не архивируются при отключении**; при повторном включении всё снова доступно. Отключённый модуль скрывает разделы и закрывает его API (существующий отказ `module_disabled`), но связи в БД (например, рейс ссылается на технику) сохраняются, а сквозные показатели других модулей не пересчитываются молча.
- **Защита финансовой целостности:** модуль `finance` нельзя отключить, пока у компании `engine` равен `shadow` или `new`; фоновые финансовые хуки (признание дохода, синхронизация расхода) действуют независимо от видимости раздела.
- Изменение конфигурации требует нового права `company.manage_modules` (по умолчанию Администратор), пишется в аудит (старое и новое значение, причина, пользователь).
- Смена тарифа не изменяет `CompanyModule`; недоступные по новому тарифу модули перестают работать, но их включённое состояние и данные сохраняются (понижение тарифа не теряет данные).

## 2.5. Совместимость
- `ModuleRequired("forwarding")` на текущих 22 эндпоинтах остаётся; эндпоинты финансов и документов переводятся на `finance` и `documents` одной миграцией кода после появления каталога (для существующих компаний оба включены).
- В сессии (`/api/session/`) `modules` отдаёт эффективный список (тариф ∩ компания) без изменений формата.

# 3. Расширенные маршруты и участки перевозки

## 3.1. Цели
Многоточечные маршруты, несколько мест погрузки и выгрузки, промежуточные остановки, разделение маршрута на участки, связь каждого участка с рейсом (а через рейс — с перевозчиком, водителем и техникой), распределение одного заказа или груза между несколькими рейсами, сборные перевозки. Текущая схема «погрузка — выгрузка» остаётся частным случаем.

## 3.2. Остановки маршрута (`ConsignmentStop`, развитие `ConsignmentPoint`)
Существующая таблица `ConsignmentPoint` расширяется, новая сущность не плодится:
- `seq` — порядок остановки в маршруте груза (1…N);
- `kind` — `load`, `unload`, `transit` (промежуточная), `transfer` (передача/перегрузка), `customs` (граница/таможня);
- прежние поля адреса и окна времени сохраняются;
- фактические данные: `status` (`planned`, `arrived`, `done`, `skipped`), `arrived_at`, `done_at`;
- доля груза на остановке (необязательно): `weight_kg`, `volume_m3`, `pallets` для частичной погрузки/выгрузки;
- необязательная ссылка на геозону (появится в модуле `gps`).
Ограничения: убирается уникальность `(consignment, kind)`; вводится уникальность `(consignment, seq)`; первая остановка — `load`, последняя — `unload`.
**Совместимость:** существующие точки получают `seq` 1 и 2; API сохраняет прежние поля `load` и `unload` (первая погрузка и последняя выгрузка) и добавляет список `stops`.

## 3.3. Участок перевозки (leg)
Участок — часть маршрута груза между двумя соседними остановками, выполняемая одним рейсом. Чтобы не дублировать финансовые якоря, участок реализуется как развитие существующей связи **`TripConsignment`**:
- новые необязательные поля: `from_stop`, `to_stop`, `leg_seq`, `status` (`planned`, `in_progress`, `done`, `cancelled`), доля груза на участке (`weight_kg`, `volume_m3`, `pallets`; пусто = весь груз);
- у прежних строк `from_stop` = погрузка, `to_stop` = выгрузка, доля пустая;
- уникальность `(trip, consignment)` заменяется на `(trip, consignment, from_stop, to_stop)`.
Перевозчик, водитель и техника участка берутся **из рейса** (`Trip.carrier` и, с этапа 2, ссылки на технику и водителя), а не дублируются на участке; индивидуальная подмена на участке не вводится без отдельного решения.
Участок без рейса допускается как «не назначен»: это позволяет планировать весь маршрут заранее.

## 3.4. Разделение между рейсами и сборные перевозки
- Один груз на нескольких рейсах: по участкам (разные рейсы на разных участках) или параллельно по долям (несколько рейсов на одном участке с долями, сумма долей на участке не превышает груз; пустая доля допустима только при единственном рейсе на участке).
- Один заказ на нескольких рейсах: как и раньше, через его грузы.
- Сборные перевозки: один рейс несёт грузы нескольких заказов (признак `Trip.is_consolidated` сохраняется и вычисляется по заказам участков).
- Разделение груза на дочерние грузы не вводится: идентичность груза, документы и счета сохраняются; долями управляют участки.

# 4. Передачи груза и перегрузки

## 4.1. Передача (`CargoTransfer`)
Неизменяемая запись о передаче груза на остановке `transfer`: `consignment`, `stop`, `from_trip`, `to_trip`, `from_carrier`, `to_carrier` (копия на момент передачи), `carrier_changed`, `transferred_at`, количество (`weight_kg`, `volume_m3`, `pallets`), кто принял и подтвердил (`confirmed_by`, `confirmed_at`), заметка, вложения (документы приёма-передачи — через механизм вложений этапа 3 ТЗ). Исправления делаются новой записью-сторно, а не правкой (история передач не теряется).
Виды: передача другому перевозчику, перегрузка между транспортными средствами одного перевозчика, перегрузка на склад (остановка `transfer` без немедленного следующего рейса).

## 4.2. Местонахождение и этап
- Журнал `ConsignmentEvent` (только добавление): `arrived`, `loaded`, `departed`, `transferred`, `unloaded`, `delivered`, `skipped`, с остановкой, участком, временем, пользователем и источником (`manual`, `driver_app`, позже `gps_hint`).
- Производные поля груза (пересчитываются сервисом из журнала): `current_stop`, `current_leg`, `location_status` (`planned`, `in_transit`, `at_stop`, `delivered`).
- GPS-координаты техники могут показываться рядом как справка, но **не привязываются** к рейсу и грузу автоматически (требование ТЗ 12.3).

## 4.3. Права
Отдельное действие `consignments.transfer` (подтверждение передачи) по умолчанию у Администратора, Менеджера и Диспетчера; водитель может инициировать запись из приложения, подтверждает уполномоченный пользователь (как для сцепок по ТЗ 8.3).

# 6. Обновлённая карта моделей

```
Platform (без company):    Module ── Plan.modules ── ActivityProfile
Company (tenant):          CompanyModule ─ Company
Forwarding:  Client, Carrier, Order ─┬─ Consignment ─┬─ ConsignmentStop (seq, kind, status, доли)   [расширено]
                                     │                ├─ ConsignmentEvent (журнал)                  [новое]
                                     │                └─ CargoTransfer (передачи)                   [новое]
                                     └─ Trip ── TripConsignment = участок (from_stop,to_stop,leg_seq,status,доли) [расширено]
Finance (G1, без изменений):  Income ─ Order;  Expense ─ Trip;  ExpenseAllocation ─ (Order, Trip);  Invoice ─ Order/Trip
Этап 2 (после дополнения):  Vehicle, Driver, назначения → Trip.vehicle/trailer/driver; участок берёт их из рейса
```

Миграции данных: (1) `CompanyModule` из `Company.modules`; (2) `seq` и признак видов у существующих точек; (3) `from_stop/to_stop/leg_seq/status` у существующих строк `TripConsignment`; (4) начальные `ConsignmentEvent` не создаются (журнал начинается с момента включения), `location_status` вычисляется по статусу груза. Все миграции аддитивные, без потери данных, обратимые, с RLS на новых tenant-таблицах и проверкой под `logistix_app`.

# 8. Критерии приёмки и тестовые сценарии

**Модули**
- Модуль, не входящий в тариф, нельзя включить (сервер). Включённый компанией, но отсутствующий в тарифе, не работает.
- Нельзя включить модуль без `requires`; нельзя отключить модуль с включёнными зависимыми; `finance` нельзя отключить при `engine ∈ {shadow, new}`.
- Отключение и повторное включение: данные модуля неизменны, API отвечает `module_disabled` и затем снова работает.
- Три уровня независимы: смена тарифа, конфигурации и роли дают ожидаемую комбинацию доступа (матрица тестов).
- Аудит конфигурации; право `company.manage_modules` назначается штатно; изоляция компаний и RLS под `logistix_app`.
- Существующие компании после миграции работают как прежде (все прежние тесты).

**Маршруты и участки**
- Заказ с несколькими погрузками/выгрузками и промежуточной остановкой создаётся и редактируется; порядок, окна времени, статусы остановок.
- Старые клиенты API с `load/unload` работают без изменений; документы со старыми шаблонами рендерятся; новые ключи `stops` доступны.
- Участки: назначение на разные рейсы, параллельные доли, проверка суммы долей, пересчёт `is_consolidated`, переназначение.
- Миграция участков и точек на базе с данными: старые рейсы и грузы идентичны по смыслу, повторное применение безопасно.

**Передачи и трекинг**
- Передача другому перевозчику и перегрузка между ТС: запись неизменяема, исправление сторно, история сохраняется; права и подтверждение.
- `location_status` и текущий этап корректны на всех шагах; журнал событий; водитель инициирует, уполномоченный подтверждает.
- GPS не привязывается к рейсу автоматически.

**Финансовая совместимость**
- Заказ с двумя рейсами двух перевозчиков и незавершённым вторым участком: доход не признаётся; признаётся после доставки (R-1); повторное событие не создаёт второй доход.
- Расход на каждый рейс создаётся отдельно; распределение по заказам рейса; прибыль заказа суммируется по всем рейсам.
- Отмена рейса одного из участков не создаёт доход; все прежние финансовые тесты G1 проходят без изменений.
- Сверка и перенос `migrate_finance`/`reconcile_finance` на данных с участками дают нулевые расхождения.
