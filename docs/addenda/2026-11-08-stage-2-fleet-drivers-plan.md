# Этап 2 «Автопарк и водители»: план реализации

Основание: разрешение заказчика (2026-11-08), архитектурное дополнение v1.1, ТЗ по модульной архитектуре и тарифам (единое актуальное ТЗ от 2026-11-08). Ограничения прежние: без слияния в `main`, миграций демо/production, переключения компаний на `engine=new`, платных сервисов.

## Принципы
- Новые приложения `apps/fleet` и `apps/drivers` (модули каталога `fleet` и `drivers`, `requires = [core]`, друг от друга и от `forwarding` не зависят). Рейсы остаются в `logistics`: назначение техники и водителя на рейс - необязательные ссылки `Trip.vehicle`, `Trip.driver` (null), доступные, только если включён соответствующий модуль; свободные поля `vehicle_plate`, `driver_name` сохраняются (совместимость, не удаляются).
- Доступ к API: `ModuleRequired("fleet")` / `ModuleRequired("drivers")` + RBAC (`fleet.*`, `drivers.*`); данные при отключении модуля не удаляются.
- Тарифная готовность: создание техники и водителей проходит через `billing.services.check_limit` (ключи `max_vehicles`, `max_drivers`); обобщение лимитов - этап T3. Тарифные зависимости в код не зашиваются.
- Каждая таблица - tenant (`TenantModel`, RLS, проверка под `logistix_app` после миграции), мягкое удаление там, где это принято в проекте, аудит.
- Участок рейса наследует технику и водителя из рейса (решение заказчика); подмены на участке нет.
- Финансы: в этапе 2 деньги не добавляются; затраты по технике/водителю позже через `ExpenseAllocation` (G1), параллельной финансовой системы нет.

## Подзадачи (каждая: миграции, тесты, RLS, CI)
- **2.1 Drivers:** `Driver` (ФИО, телефон, статус, ИИН, права/категории, ссылка на пользователя необязательна), `DriverDocument` (вид, номер, срок действия, файл через вложения), справочные виды документов; права `drivers.view/create/update/delete`; API, интерфейс, лимит `max_drivers`.
- **2.2 Fleet:** `Vehicle` (тягач/полуприцеп/грузовик, госномер, VIN, тип кузова, грузоподъёмность, статус), `VehicleDocument`, страховка `Insurance` (вид, полис, срок), лимит `max_vehicles`; права `fleet.*`.
- **2.3 Назначения:** `Trip.vehicle`, `Trip.driver` (+ прицеп необязателен), проверка занятости, выбор в карточке рейса; отображение в участках.
- **2.4 Обслуживание:** ТО, ремонт, запчасти, топливо, пробег, история.
- **2.5 Документы:** поставщики документов для техники, водителей, страховок (универсальный субъект `fleet.vehicle`, `drivers.driver`, `fleet.insurance`); виды: акт обслуживания, приказ, справка, путевой лист.
- **2.6 Интерфейс и меню:** разделы «Техника», «Водители» (по модулю и праву); комплексный UX/UI - после основной функциональности.
- **Driver App** и **GPS** - отдельные шаги после 2.1-2.6.

## Критерии приёмки
1. Компания без `fleet`/`drivers` работает как раньше; с ними - создаёт и назначает технику и водителей.
2. Отключение модуля скрывает меню и закрывает API (403 `module_disabled`), данные сохраняются, повторное включение возвращает доступ без дублей.
3. RLS под `logistix_app`, изоляция компаний, права, аудит - проверены на каждую новую таблицу.
4. Лимиты `max_vehicles` и `max_drivers` блокируют новые записи сверх лимита, существующие не затрагиваются.
5. Старые поля рейса (`vehicle_plate`, `driver_name`) и API не ломаются.
