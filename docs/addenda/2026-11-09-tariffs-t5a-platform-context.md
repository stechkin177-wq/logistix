# T5-A. Платформенный контекст: единый вход и роли платформы

Дата: 2026-11-09. Минимальный объём по решению владельца проекта.

## Что сделано
- **Единая страница входа.** После проверки пароля сервер сам определяет контекст:
  платформенная роль → Центр управления (`/platform`), иначе → компания. В ответе входа поле
  `context` (`platform` | `company`).
- **Владелец входит без Membership.** Для собственных перевозок владелец заводит отдельный
  аккаунт и состоит в своей компании как обычный пользователь.
- **Две платформенные роли** (`User.platform_role`): `owner` — «Владелец платформы» (всё),
  `admin` — «Администратор платформы» (просмотр + подписки компаний; без тарифов и блокировок).
  Реестр прав — `apps/core/platform.py` (`ROLE_PERMISSIONS`), расширяется без отдельной системы ролей.
- **Superuser/is_staff платформенных прав не дают.** `create_superuser` роль не назначает.
  Прежний флаг `is_platform_admin` удалён; существующим администраторам миграция `core.0023`
  выставила роль `owner` (других платформенных аккаунтов не было).
- **Независимость прав.** Платформенный токен (`ctx=platform`, без `company_id`) не открывает
  данные компаний (403 `company_context_required`), токен компании не открывает платформенные API
  (403 `platform_context_required`). Роль проверяется по БД на каждом запросе: снятие роли действует
  сразу. Переключение в платформу: `POST /api/auth/switch-company/ {"context":"platform"}` только при
  наличии роли; в компанию — `{"company_id": N}` только при активном членстве.
- **`GET /api/platform/session/`** — сессия Центра управления: пользователь, роль, права, компании.
- **Журнал платформы** (`BillingEvent`): новые виды `auth` (вход, неудачный вход, смена контекста,
  назначение роли; с IP, пароль не пишется) и `company` (блокировка/возврат компании с причиной).
- **Блокировка/возврат компании** (только владелец): `POST /api/platform/subscriptions/{id}/block|unblock/`
  с обязательной причиной; данные компании не затрагиваются.
- **Первый владелец**: `manage.py create_platform_owner <email>` (пароль — интерактивно или
  `PLATFORM_OWNER_PASSWORD`), роли — `manage.py set_platform_role <email|телефон> owner|admin|none`.
  Публичного способа стать владельцем нет.
- **Интерфейс:** отдельная оболочка `/platform` (тарифы, подписки компаний, история), не зависит от
  тарифов и модулей; «Открыть компанию…» и обратный «Центр управления» без повторного входа,
  кэш запросов при смене контекста очищается. Платформенные разделы убраны из меню компании.

## Не входит (отдельные задачи)
TOTP/2FA (обязателен до production), управление платформенным персоналом из интерфейса, обзор,
пользователи платформы, статус системы, настройки платформы, реализация Support Access.

## Контракт Support Access (только архитектура, не реализовано)
- Доступ платформы к данным компании — только по явному разрешению компании (журналируемое,
  с ограниченным сроком и областью), отдельный контекст `ctx=support` с `company_id` и `support_grant_id`.
- Грант создаёт администратор компании (`SupportGrant`: компания, роль платформы, срок, область
  «только чтение», причина, `revoked_at`); токен support-контекста выдаётся при наличии активного гранта.
- Все действия в support-контексте пишутся в аудит компании и в платформенный журнал; финансовые и
  коммерческие данные по умолчанию недоступны (область гранта задаёт, что открыто).
- Платформенные роли сами по себе доступа к данным компаний не дают (как сейчас).
