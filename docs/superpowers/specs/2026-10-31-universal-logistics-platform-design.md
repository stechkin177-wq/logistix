# Logistix — универсальная платформа для перевозчиков и экспедиторов — дизайн

Дата: 2026-10-31. Статус: утверждена владельцем, открытые вопросы раздела 13 уточнены.
Этот файл временно лежит в репозитории `truck365`. После утверждения переносится в новый отдельный репозиторий платформы.

## 1. Цель и контекст

**Цель.** Создать мультитенантную SaaS-платформу для транспортных компаний Казахстана. Компания включает режим «экспедитор», «перевозчик» или оба сразу.

**Вдохновение.** Функциональность экспедиторского контура ориентирована на демо `demo.transpro.kz` (TransPro, CRM для экспедитора). Копируются только функции и структура разделов. Код, вёрстка, тексты и брендинг TransPro не используются.

**Что переносим из `truck365`.** Бизнес-логику контура перевозчика: автопарк, обслуживание, водительское PWA, распознавание документов, Telegram-бот, интеграцию Wialon. Архитектуру (Vercel serverless, отключённый Celery, Supabase в Мумбаи) не переносим.

**Критерии успеха.**
- Экспедитор заводит клиента, заказ, груз, рейс, выставляет счёт и видит прибыль, долги и маржу.
- Перевозчик ведёт свой автопарк, назначает свою машину и водителя на рейс; водитель сдаёт отчёт с распознанными документами.
- Компания в режиме «оба» использует единый рейс для партнёра и для своей машины.
- Данные одной компании недоступны другой (проверяется тестами).
- Владелец платформы управляет тарифами, лицензиями и блокировкой компаний; первый год лицензия бесплатна, механизм оплаты по безналу работает с первого дня.
- Хостинг и данные находятся в Казахстане.

**Вне объёма первого релиза.** Расчёт ставок, онлайн-эквайринг, автосверка банковских выписок, ЭСФ и ЭЦП (не входят в проект), импорт из 4logist (обсуждается позже), мобильное приложение для менеджеров.

## 2. Этапы реализации

Каждый этап проходит собственный цикл «спецификация → план → реализация».

1. **Ядро:** компании, пользователи, роли и права, справочники, нумерация, аудит, режимы, тарифы и лицензии (структуры и проверки), оформление, дизайн-система, инфраструктура и CI.
2. **Экспедиторский контур:** клиенты, перевозчики, заказы, грузы, рейсы, консолидация, канбан, корзина.
3. **Финансы и документы:** счета, оплаты, операции, долги, шаблоны и выгрузка документов, дашборд.
4. **Контур перевозчика:** автопарк, водители, обслуживание и ремонты, Wialon, водительское PWA, распознавание отчётов, Telegram-бот.
5. **Коммуникации и платформа:** почта, мессенджер, админка платформы с ручными счетами, белая метка и свой домен, ЭСФ, импорт из 4logist.

Первый цикл реализации: этапы 1 и 2.

## 3. Технологический стек

| Слой | Выбор | Причина |
|---|---|---|
| Бэкенд | Python, Django 5, Django REST Framework | переиспользуем логику `truck365`, зрелые роли, миграции, админка |
| БД | PostgreSQL | транзакции, RLS, JSON, масштабируемость |
| Фон | Celery, Redis | OCR, опрос Wialon, письма, расписания |
| Файлы | S3-совместимое хранилище (MinIO) | документы, фото, вложения |
| Фронтенд | React, TypeScript, Vite, TanStack Query, React Router | опыт `truck365`, SPA |
| UI | Tailwind и набор компонентов в коде репозитория (shadcn/ui) | собственный дизайн, темы через CSS-переменные |
| Водители | PWA в том же монорепо | офлайн-очередь, установка на телефон |
| Бот | aiogram | уже реализован |
| Мониторинг | Sentry, базовый мониторинг серверов | ошибки и доступность |
| Языки | русский и казахский (i18n с первого дня) | рынок |

**Хостинг.** Провайдер hoster.kz (Казахстан), VPS или облако, Docker Compose: Nginx, gunicorn, Celery worker и beat, Redis, PostgreSQL, MinIO. Среды `staging` и `production`, деплой из CI. Ежедневные бэкапы БД и файлов на отдельное казахстанское хранилище, проверка восстановления с самого начала. Масштабирование: сначала мощнее сервер, затем отдельные машины для БД и воркеров. Kubernetes на старте не нужен. Закон РК о персональных данных требует хранить базы с персональными данными граждан РК на территории РК, поэтому основная БД, файлы и бэкапы находятся только на казахстанских серверах, зарубежных реплик нет. Внешние сервисы получают минимум данных: Sentry работает с очисткой персональных данных или на своём сервере; распознавание документов через Gemini или Google Vision выполняется только с согласия пользователя и с маскированием лишнего, позднее возможен переход на собственное распознавание (Tesseract). Формулировки проверяются юристом до запуска.

## 4. Архитектура

Модульный монолит. Монорепо:

```
platform/
├── backend/apps/  core, billing, forwarding, fleet, finance, drivers, comms, integrations
├── web/           панель компании и админка платформы (React)
├── driver-pwa/    приложение водителя (React PWA)
├── bot/           Telegram-бот
└── deploy/        Docker Compose, Nginx, скрипты бэкапов
```

Модули общаются через явные сервисные функции и события внутри процесса; прямые обращения к моделям чужого модуля ограничены. Это позволит позже выделить сервисы.

### 4.1 Мультитенантность
- Общая БД, у каждой клиентской записи поле `company`.
- Базовый менеджер по умолчанию фильтрует по компании из контекста запроса.
- PostgreSQL Row-Level Security как вторая линия защиты.
- Автотесты: компания A не видит данные компании B через API, поиск и экспорт.

### 4.2 Режимы компании
У компании хранится набор модулей (`forwarding`, `fleet`). От него зависят меню, доступные API и набор прав. Рейс общий для обоих режимов: исполнитель — сторонний перевозчик или собственные машина и водитель.

### 4.3 Белая метка
- Всем клиентам: название, логотип, основной цвет, тема, фирменные шаблоны документов и подпись писем.
- Платная опция старших тарифов: собственный домен (компания определяется по имени хоста), полное скрытие упоминаний платформы, включая PWA водителя.
- Реализация: настройки `CompanyBranding` превращаются в CSS-переменные; сборка одна для всех.

## 5. Ядро (этап 1)

**Сущности.**
- `Company`: название, БИН, реквизиты, банк, режимы, часовой пояс, язык, оформление.
- `User` и `Membership` (пользователь, компания, отдел, роль). Один человек может работать в нескольких компаниях. Вход по email или телефону.
- `Department`, `Role`, права как пары «раздел + действие» (просмотр, создание, изменение, удаление). Системные роли: Администратор, Менеджер, Наблюдатель, Бухгалтер, Диспетчер, Механик, Водитель; компании могут создавать свои. Права проверяются на сервере; интерфейс только скрывает недоступное.
- `Handbook` и значения справочников: статусы (заказов, грузов, рейсов, документов), валюты, ставки НДС, типы клиентов и перевозчиков, виды упаковки, способы погрузки, страны, регионы и другие. Платформа поставляет набор по умолчанию, компания расширяет его.
- `Numbering`: шаблоны номеров (`ORD-{year}-{index}`, `{order}-{n}`, `C{index}`, `СЧ-{year}-{index}`), разрядность, счётчик с возможностью ручной установки.
- `AuditLog`: изменения записей и входы в систему.
- Мягкое удаление и корзина для основных сущностей.

**Тарифы и лицензия.**
- `Plan`: тип оплаты (`monthly`, `yearly`, `lifetime`), лимиты (пользователи, машины, заказы в месяц, распознавания документов), включённые модули и опции (`white_label`, `custom_domain`, интеграции). Для пожизненной лицензии срок окончания пустой, лимиты и опции действуют бессрочно.
- `Subscription`: компания, тариф, период, статус `trial | active | grace | readonly | blocked`, дата окончания, признак бесплатного периода.
- Первый год лицензия бесплатна: акционный период с датой окончания. После окончания: предупреждения, затем `readonly`, затем `blocked`. Данные сохраняются.
- `PlatformInvoice` и оплата: счёт выставляется вручную или по расписанию, оплата по безналу отмечается вручную в админке платформы. Структура допускает добавление онлайн-оплаты позже.
- Единая проверка лимитов и режимов в общем слое.

## 6. Экспедиторский контур (этап 2)

```
Client ──< Order ──< Consignment >──< Trip >── Carrier
              │                         └── Vehicle / Driver (чужие или свои)
              └──< OrderService (строки: доход / расход)
```

- `Client`, `Carrier`: БИН/ИНН, тип, статус, контактные лица, банк. У перевозчика рейтинг, у клиента лимит кредита.
- `Order`: номер, клиент, договор, контактное лицо, менеджер, экспедитор, дополнительные менеджеры, наше юрлицо, ставка клиента, валюта, условия перевозки, срок доставки, отсрочка и её условие, комментарий, статус.
- `Consignment` (груз): наименование, вес, объём, паллеты, упаковка, точки погрузки и выгрузки (окно времени, адрес, способ, контакт, координаты), собственные статусы (Принят, На складе, В пути, Доставлен, Выдан).
- `Trip` (рейс): перевозчик или собственный исполнитель, машина, водитель, цена перевозчика, статус. Рейс может включать грузы нескольких заказов (консолидация) со своим сквозным номером.
- `OrderService`: строки дохода и расхода (ставка, простой, доп. услуги); из них считаются прибыль и маржа.
- Интерфейс: список заказов с фильтрами и выгрузкой в Excel, канбан по статусам, форма создания заказа в четыре блока (контакты, ценник, груз, маршрут), подсветка «без перевозчика», история смены статусов, корзина.

## 7. Финансы и документы (этап 3)

- Выставленные счета: из заказа, номер по шаблону, срок оплаты из условий отсрочки, статусы (ожидает оплаты, частично, оплачен, просрочен), остаток и просрочка.
- Полученные счета: от перевозчиков, привязка к рейсу и заказу.
- Оплаты: ручная отметка, частичные оплаты.
- Операции: доход и расход по строкам заказа, фильтры по категории и периоду, итоговая разница.
- Долги: по клиентам выставлено, не получено, просрочено, лимит кредита; предупреждение при превышении лимита.
- Валюты и курсы (KZT, RUB, USD, EUR), ставки НДС.
- Шаблоны документов: договор, заявка клиента, договор-заявка перевозчику, акт, счёт на оплату, CMR, письмо на бланке; подстановка данных заказа, выгрузка в PDF и DOCX, отправка письмом.
- Дашборд: активные и завершённые заказы, заказы по статусам, прибыль и маржа за месяц, долг клиентов, заказы без перевозчика.
- ЭСФ и ЭЦП в проект не входят.

## 8. Контур перевозчика (этап 4)

- Автопарк: машины, прицепы, документы с напоминаниями о сроках.
- Водители: профиль, привязка к машине, документы.
- Обслуживание и ремонты: регламенты по пробегу и времени, журнал ремонтов и расходов (раздел «Ремонты» в `truck365` пока пустой и реализуется заново).
- Wialon: пробег, местоположение, трек рейса, фоновая синхронизация.
- Расходы по рейсу: топливо, платные дороги, зарплата водителя, прочее, из отчёта водителя.
- Водительское PWA: вход по телефону, назначенные рейсы, смена статусов, отчёт по рейсу с фото чеков и накладных, распознавание (Gemini или Google Vision) с подстановкой сумм и дат и подтверждением водителем, офлайн-очередь отправки.
- Telegram-бот: привязка пользователей и водителей, уведомления о рейсах, статусах, просроченных счетах, сроках документов и ТО.

## 9. Коммуникации и платформа (этап 5)

- Почта (ящики, отправка счетов и писем, связь с заказом) и мессенджер внутри компании.
- Админка платформы: компании, тарифы, подписки, ручные счета и отметки оплат, блокировка, пробные периоды, поддержка.
- Белая метка и свой домен для старших тарифов. Импорт из 4logist обсуждается отдельно позже.

## 10. Нефункциональные требования

- **Безопасность:** серверная проверка прав, RLS, аудит входов, хранение секретов вне репозитория, защита загрузок файлов, резервные копии и проверка восстановления.
- **Качество:** автотесты бэкенда (изоляция компаний, права, лимиты, нумерация, финансовые расчёты), типизация и линтинг фронтенда, CI на каждый коммит.
- **Доступность интерфейса:** адаптивность, проверка цветов на доступность, компактная плотная вёрстка таблиц.
- **Локализация:** все тексты через i18n, русский и казахский.
- **Производительность:** постраничные списки, индексы по компании и датам, тяжёлые операции только в фоне.

## 11. Обработка ошибок

- Единый формат ошибок API, понятные сообщения на русском и казахском.
- Фоновые задачи с повторными попытками и журналом; сбои OCR и Wialon не блокируют работу, запись помечается «требует ручного ввода».
- При превышении лимитов тарифа пользователь получает явное объяснение и ссылку на смену тарифа.

## 12. Тестирование

- Бэкенд: pytest, фабрики данных, обязательные тесты изоляции компаний на каждом клиентском эндпоинте.
- Фронтенд: проверка типов, линтинг, сборка, компонентные тесты ключевых форм, сквозные сценарии (создание заказа до счёта) на staging.
- Перед релизом: проверка восстановления из бэкапа и нагрузочный прогон списков.

## 13. Принятые решения и открытые вопросы

**Принято.** Название продукта Logistix. Тарифы: месячный, годовой и пожизненная лицензия, цены определяются позже. Хостинг hoster.kz, данные только в Казахстане. ЭСФ и ЭЦП не делаем. Импорт из 4logist обсуждаем позже.

**Открыто (не блокирует первый цикл).**
- Домен продукта и цены тарифов.
- Юридическая проверка требований к хранению и передаче персональных данных.
- Формат согласия на распознавание документов за границей и решение по собственному распознаванию.
