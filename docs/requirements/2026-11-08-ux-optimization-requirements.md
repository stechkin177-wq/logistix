# Требования к комплексной UX/UI-оптимизации LogistiX

Статус: зафиксировано по запросу заказчика (2026-11-08). Реализуется ПОСЛЕ функциональных этапов;
текущую разработку не останавливает. Принцип: внутри система остаётся сложной, для пользователя
ежедневная работа простая; упрощаем интерфейс и число действий, а не надёжность и возможности
(RLS, права на сервере, Finance G1, валютные снимки, закрытие периодов, аудит, защита от двойного
учёта, история передач, сборные и многоэтапные перевозки не сокращаются). Новые сущности, поля и
настройки «про запас» не добавляются.

## Матрица предложений

| № | Предложение | Поддержано архитектурой | Что нужно | Влияние на данные/финансы |
|---|---|---|---|---|
| 1 | Заказ: основные поля + раскрываемый блок | Да (поля уже необязательные: контракт, контакт, экспедитор, условия) | Только интерфейс. Автоподстановка: менеджер = текущий пользователь, юрлицо = единственное/по умолчанию, валюта = базовая компании. Подстановки с клиента (контакт, условия) - backend: поле «последние значения клиента» читаем из его прошлых заказов (без новых полей) | Нет |
| 2 | Два уровня работы с грузом/маршрутом | Да (Order, Consignment, ConsignmentPoint, Trip, TripConsignment, CargoTransfer, ConsignmentEvent сохраняются) | Интерфейс: простой режим «погрузка + выгрузка», расширенный - остановки, склады, перегрузки | Нет |
| 3 | Рейс из карточки заказа одной кнопкой | Да (единый сервис `create_trip`) | Интерфейс; новый вызов того же сервиса, второй логики не создаётся | Нет |
| 4 | Финансы: сводка на первом экране, остальное во вкладках | Да (вкладки уже есть: Счета, Оплаты, Доходы, Расходы…) | Интерфейс; сводка читает те же отчёты. Переход «создать/привязать расход» из карточки ТО и заправки | Нет: деньги только в G1, в `fleet` лишь ссылка `expense` |
| 5 | Единая карточка техники (6 вкладок), предупреждения на главном экране | Частично: данные есть (документы, страховки, ТО, заправки, расход, напоминания `/api/fleet/reminders/`) | Интерфейс; для вкладки «История событий» нужен backend: лента по технике из аудита и записей | Нет |
| 6 | Пробег и топливо | Реализовано по решению заказчика (раздел 6) | Backend сделан; интерфейс - ввод пробега в действии «Начать рейс» и «Завершить» | Только данные fleet, G1 не затрагивается |

| 8 | Фильтры: поиск, статус, один основной; остальное в «Дополнительные фильтры» | Да | Только интерфейс; единый компонент для заказов, рейсов, техники и т.д. | Нет |
| 9 | Тарифы и модули скрыты от обычного пользователя | Частично (профили, `CompanyModule`, тарифы есть) | Этапы T1-T5 и профили; интерфейс - выбор профиля и тарифа при создании компании | Нет (внутренняя логика остаётся) |

## Результаты проверки (пункт 6)

### 6.2 Расход топлива - исправлено
Было: заправки без пробега полностью исключались, их литры терялись. Сейчас: якорями служат
только полные заправки С пробегом; литры всех заправок между двумя якорями суммируются, даже если
у них нет пробега; заправка без пробега не определяет расстояние. Пример заказчика
(полная 10 000 км → частичная без пробега 100 л → полная 10 800 км, 130 л): (100 + 130) / 800 ×
100 = 28,75 л/100 км. Покрыто тестами (`apps/fleet/tests/test_fuel_stats.py`): частичная без/с
пробегом, полная без пробега, заправки до первого и после последнего якоря, несколько сегментов
(взвешенное среднее), нулевое расстояние, недостаточно данных, порядок по времени.

### 6.1 Пробег - решение заказчика (заменяет прежние предложения)
Найденные ранее дефекты (устаревшие показания при правке и удалении заправок/ТО, ложные
отклонения, «сироты») снимаются упрощением логики, правка модели показаний-связей НЕ нужна:
1. Официальный пробег (`MileageReading`) фиксируется только при выезде в рейс (переход в «В пути»
   не из «Выгрузки») и после завершения рейса по отчёту водителя; тягач и полуприцеп раздельно.
   Передаётся необязательно вместе со сменой статуса (`vehicle_km`, `trailer_km`) или позже
   действием `POST /api/trips/{id}/odometer/` (внесение/исправление: одно показание на рейс,
   технику и фазу). Показания не убывают; пробег завершения не меньше пробега выезда.
2. Пробег в заправках, обслуживании, страховках, осмотре и других записях - справочный: он ничего
   не изменяет в официальном пробеге и не проверяется против него.
3. Настройка «Сверять пробег по GPS» - флаг `gps_check` у каждой единицы техники.
4. Включённая сверка показывает официальный пробег, пробег по GPS и разницу
   (`GET /api/vehicles/{id}/mileage-check/`). Нет данных GPS - «данные недоступны».
5. Допустимое расхождение - одна настройка компании `FleetSettings.gps_mismatch_km`
   (по умолчанию 100 км, `GET/PATCH /api/fleet/settings/`); больше порога - предупреждение.
6. GPS не меняет официальный пробег и не создаёт записей в его истории; сложных отчётов,
   статусов и ручного подтверждения сверок нет. Подключение GPS и сверка независимы: GPS может
   использоваться для местоположения при выключенной сверке. Модуль gps подключает источник
   пробега через `fleet.services.register_gps_source`.
7. Начальный пробег при подключении техники - отдельное значение `Vehicle.initial_odometer_km`,
   не запись истории: нижняя граница для первого показания по рейсу и значение «официального
   пробега» до первого рейса. Произвольных ручных показаний нет.
8. Сверка показывает время последнего полученного значения GPS (`gps_received_at`); источник GPS
   возвращает пару (км, время получения).
`/api/mileage/` - только чтение. Миграция fleet.0003 удалила показания источников fuel и service
(дубли справочного пробега); fleet.0004 перенесла самое раннее ручное показание каждой техники в
начальный пробег (если он не задан) и удалила остальные ручные записи. Миграции fleet на
демо/production не выполнялись, ручных показаний там нет.
Вложения (чеки, фото, акты) отложены до отдельного решения по бесплатному хранилищу.

## Найденные при изучении проекта лишние действия и сложности
1. Форма заказа показывает сразу ~13 полей, в том числе необязательные (договор, номер клиента,
   условия оплаты, срок доставки); менеджера и юрлицо можно подставлять автоматически.
2. Фильтры заказов - 11 элементов в одном ряду (даты создания/погрузки/завершения парами).
3. Статус рейса - выпадающий список всех значений справочника; нужна одна кнопка следующего шага.
4. У рейса теперь два способа указать машину/водителя: свободные поля `vehicle_plate`/`driver_name`
   и ссылки; при выборе техники/водителя текстовые поля надо скрывать (сервер уже заполняет их).
5. В рейсе параллельно живут `price` (алиас) и `carrier_price`; в интерфейсе нужно одно поле.
6. Напоминания по ТО, документам и страховкам доступны только через API: нужны блок на главном
   экране автопарка и (позже) уведомления.
7. Финансы открываются на «Счетах»; пользователю чаще нужна сводка: доходы, расходы, прибыль, долги.
8. Создание расхода по ТО/заправке сейчас возможно только в разделе «Финансы» - нужен переход из
   карточки с предзаполнением (без дублей: проверка, что расход ещё не привязан).
9. Корзина, аудит и справочники занимают отдельные разделы меню - в простом режиме их можно
   убрать под «Ещё».

## Порядок
1. (сделано) Проверка и исправление расчёта топлива; диагностика пробега, решение - на согласование.
2. Продолжение функциональных этапов по утверждённому плану (2.5-2.6, тарифы T1-T5, профили).
3. Комплексная оптимизация интерфейса по этому документу.
4. Перед внедрением - проверка, что упрощение не нарушило права, ограничения модулей и G1.
