# Аудит модульной независимости (перевозчик без «Экспедирования») и место функционала простоев

Дата: 2026-11-08. Код не менялся. Аудит по коду ветки `claude/epic-bohr-380x91` (быстрый, по ключевым точкам; без прогона тестов).

## 1. Найденные зависимости (блок А)

Права (RBAC): коды `orders.*`, `trips.*`, `consignments.*`, `carriers.*`, `clients.*` от модуля не зависят — отключение модуля прав не ломает, но выдача прав на экспедиторские операции отдельно не отделена (см. п. 5).

## 2. Целевая архитектура (блоки Б, В)
Принцип: **общий слой перевозки отделяется от экспедиторских процессов. Код остаётся в `apps/forwarding` (физически не переносим — риск и миграции), меняется только модульная привязка.**

Новый модуль каталога **`logistics`** («Перевозки»): общий слой.
- Остаётся общим: `Client`, `Contact`, `Order`, `Consignment`/остановки (`ConsignmentPoint`), `Trip`, `TripConsignment` (участки), `CargoTransfer` и `ConsignmentEvent` (перегрузы, склады — нужны и перевозчику), `OrderService` (допуслуги), `OrderStatusHistory`, дашборд.
- `forwarding` («Экспедирование») — расширение, только экспедиторское: справочник `Carrier` (сторонние перевозчики), назначение рейса стороннему перевозчику (`Trip.carrier`), `carrier_price`, расход «перевозчику за рейс» и его синхронизация, передача заказа перевозчику с контролем, `Order.forwarder`/роли экспедитора, документы «заявка перевозчику». `forwarding.requires = [logistics]`.
- `finance.requires = [core, logistics]` (причина: доходы/расходы ссылаются на заказы и рейсы). Блоки по перевозчику (carrier_transport, carrier_price sync) активны только при `forwarding`.
- `documents`: без жёсткой зависимости (уже `requires core`); шаблоны, требующие перевозчика (`_check_trip_carrier`), доступны при `forwarding`; для собственных рейсов добавить виды (ТТН/путевой лист) позже.
- `driver_app.requires = [drivers, logistics]`; `fleet`, `drivers`, `gps`, `notifications`, `analytics` — `requires core` (gps — fleet), `enhances logistics`.
- Миграция данных: для всех компаний с включённым `forwarding` создать `CompanyModule(logistics)`; тарифы (`plan.modules`) дополнить `logistics` везде, где есть `forwarding`; `Company.modules` синхронизируется проекцией. Ничего не удаляется.
- Эндпоинты: `ModuleRequired("logistics")` для общего слоя; `ModuleRequired("forwarding")` только для `Carrier` и операций назначения стороннему перевозчику/ синхронизации расхода. Меню: тот же разрез.
- Права: добавить `carriers.*` как экспедиторские (только при `forwarding`); остальные коды без изменений — обычные заказы и рейсы не зависят от прав на экспедирование.

## 3. Профили (блок Г)
- **Перевозчик (carrier):** `logistics, fleet, drivers, finance, documents` (+ опц. driver_app, gps, notifications, analytics).
- **Экспедитор (forwarder):** `logistics, forwarding, finance, documents`.
- **Совмещённая (forwarder_carrier):** `logistics, forwarding, finance, documents, fleet, drivers`.
Валидация `unmet_requirements`, `apply-profile` и тесты каталога обновляются. Совмещённая компания использует одни и те же заказы/рейсы: рейс либо с `carrier` (сторонний), либо без (собственный, позже — с техникой/водителем из `fleet`/`drivers`); смешанный заказ — участки на разные рейсы (уже поддержано).

## 4. Совместимость с G1 и 1.5 (блок Е)
- R-1, участки, передачи, события, история: логика остаётся в тех же приложениях; меняются только модульные ворота и каталог. Риск низкий.
- Проверить в G1: `engine=new` и сверка для компании без `Carrier`/`carrier_price` (нулевые расходы перевозчику; `completed_status`, R-1 по собственным рейсам); хуки `finance.hooks` при `carrier is None`.
- Отключение `forwarding` у компании с рейсами сторонних перевозчиков: данные не удаляются; guard отключения (`register_disable_guard`) блокирует отключение при активных рейсах с перевозчиком/расходами, пока не решено заказчиком.
- RLS: новая запись `CompanyModule` под `logistix_app` — проверка после миграции (по принятому порядку).

## 5. Остановки и простой (место функционала)
Не новый модуль, не новый пункт меню, не новая финансовая сущность.
- **Хранение времени:** расширить существующую `ConsignmentPoint` (остановка) полями факта: `planned_arrival`, `arrived_at`, `departed_at`, `wait_reason`, `comment`; вложения — через `documents`. Остановка уже имеет вид (load/unload/transit/transfer/customs); добавить «склад/другое». Остановка привязана к грузу, а простой — к рейсу: рейс получает остановки через участки (`TripConsignment`).
- **Условия:** `DemurragePolicy` (настройки, не деньги): владелец — клиент, перевозчик или заказ/рейс (приоритет: рейс > заказ > договор клиента/перевозчика > по умолчанию компании); поля: бесплатные часы, режим (по рейсу/по остановке), учитываемые типы остановок, исключённые причины, тариф и единица (сутки/час), округление (полные сутки/пропорционально), валюта. Без зашитых 3 суток.
- **Расчёт:** чистая функция по остановкам рейса и политике → `DemurrageCalc` (снимок: общее/бесплатное/оплачиваемое время, сумма, версия политики, ввод вручную + причина). Две независимые стороны: `client` и `carrier`.
- **Деньги — только через G1:** сторона клиента → `Income` вида «дополнительная услуга» заказа (отдельная строка, не меняет `client_rate`), сторона перевозчика → `Expense` рейса (вид `other`/доля на рейс) с `source=demurrage` и ключом идемпотентности `(trip, side)`; пересчёт обновляет существующую запись, а не создаёт вторую (по аналогии с `carrier_price_sync`). Закрытый период, обратное датирование, валюты и снимок курса — штатные правила G1.
- **Аудит:** любое изменение времени, политики, суммы и ручной корректировки — в журнал действий с причиной; права `trips.confirm_times` и `trips.adjust_demurrage`; водитель фиксирует через мобильное приложение (после `driver_app`), подтверждает сотрудник.
- **Отображение:** блок «Остановки и простой» в карточке рейса; в карточке рейса и заказа — строки «перевозка / простой / допуслуги / итого»; контекст документов `trip.legs[]` получает поля времени и сумм; аналитика — после `analytics`.
- **Зависимость от модулей:** остановки и расчёт — в `logistics`; сторона клиента — при `finance`; сторона перевозчика — при `forwarding`+`finance`.
- **Очерёдность:** по рекомендации заказчика текущую разработку не останавливаем: требования закладываются в схему остановок и ожидают этапа маршрутов/автопарка.

## 6. Порядок реализации
1. Каталог + профили + миграция `logistics` (CompanyModule, тарифы), тесты каталога/зависимостей и RLS под `logistix_app`.
2. Переключение ворот эндпоинтов и меню: общий слой — `logistics`, `Carrier` и назначение стороннему — `forwarding`.
3. Финансы: зависимость от `logistics`; проверка сценариев собственного рейса (без перевозчика) в R-1, сверке, расходах рейса.
4. Документы: виды для собственных рейсов, условная доступность шаблонов по перевозчику.
5. Этап 2 (автопарк/водители) уже над `logistics`; затем остановки с фактическим временем и простоем (п. 5).

## 7. Риски
- Миграция тарифов/модулей у существующих компаний (одна дополнительная запись, обратимо).
- Затронутые тесты: каталог, профили, nav, ModuleRequired — много, но механические.
- Расхождение смысла `Order.forwarder` (пользователь) и модуля; переименовать в интерфейсе, поле не трогать.
- Автосоздание расхода из цены рейса должно быть строго условным (`carrier` задан).
- Простой: риск двойного учёта при пересчёте — закрывается ключом идемпотентности и обновлением, а не созданием.

## 8. Критерии приёмки
1. Компания `carrier` без `forwarding`: заказы, грузы, остановки, рейсы (без `Carrier`), финансы, документы доступны; эндпоинты `Carrier` — 403 `module_disabled`.
2. Компания `forwarder` и `forwarder_carrier` работают как прежде; существующие данные и тесты G1 и 1.5 без регрессий.
3. `finance` включается без `forwarding`; `forwarding` без `logistics` — нельзя.
4. Меню и ворота API согласованы; права на `carriers.*` не влияют на обычные заказы и рейсы.
5. Миграция идемпотентна, обратима, RLS под `logistix_app` проверен; сверка `engine=new` для собственных рейсов успешна.
6. Простой: расчёт по политике без зашитых значений; одна запись дохода/расхода на сторону; повтор пересчёта не создаёт дубль; аудит всех правок.
