# Техническое предложение: функциональные дополнения LogistiX (этап 3)

Статус: предложение на решение владельца. **Ничего из описанного не реализовано** - код не менялся.
Основа: сравнение с TransPro (2026-11-12), результат этапов 1-2 (дизайн-система, страницы-карточки,
сквозные `EntityHistory`/`EntityComments`) и изучение текущего кода.

## 0. Рамки и принципы

Из решений владельца (остаются в силе):

1. React + Vite и текущая архитектура backend не меняются; рабочая бизнес-логика не переписывается.
2. **Финансовые расчёты, правила и архитектура не меняются; дублирующих финансовых сущностей не создаём.**
   Деньги по-прежнему живут только в `apps/finance` (Finance G1). Новые таблицы вне финансов
   хранят лишь ссылки (`invoice_id`, `order_id`) и не считают суммы.
3. `engine=new` не включается; существующие функции и совместимость не удаляются.
4. Без платных сервисов и инфраструктуры. Мессенджер, база знаний, платные интеграции - не проектируются.
5. Каждая новая таблица компании: `TenantModel` + RLS (`enable_rls`, проверка `check_rls`),
   права на сервере, мягкое удаление там, где запись можно «вернуть из корзины».

Что проверено в коде и меняет оценку объёма (подробности в разделах ниже):

| Факт | Следствие |
|---|---|
| Счета уже привязаны к заказу (`Invoice.order`, `Invoice.trip`, фильтр `?order=`), блок `OrderInvoicesBlock` уже стоит во вкладке «Финансы» заказа | Пункт 1 - почти только перенос и оформление интерфейса |
| Кредитный лимит уже есть (`Client.credit_limit`) и **уже проверяется** при выставлении счёта (`credit_limit_exceeded`, с переопределением и записью в аудит); в долгах есть столбец «Лимит» | Пункт 2 - показ и предупреждение, не новая логика денег |
| Редактор справочников **уже есть** (`/settings/handbooks`: группы, значения, создание, правка, активность, удаление, права `handbooks.*`) | Пункт 6 - доработка, а не новая функция |
| `audit.log_login()` написана, но **нигде не вызывается** (проверено по коду) - записей «вход» в журнале нет | Пункт 7 требует подключения к входу, это изменение auth-потока |
| Журнал аудита уже пишется для заказов, рейсов, клиентов, перевозчиков, техники, водителей (`AuditedMixin`) и читается через `/api/audit/` | Пункт 9 (история) уже работает через `EntityHistory`; комментариев в backend нет |
| Отправки почты в проекте нет вообще (нет SMTP-настроек, нет модели письма) | Пункт 4 - самый крупный и единственный, требующий решения по инфраструктуре |
| «Метки» (теги) в моделях отсутствуют | Пункт 3 - новая простая сущность |
| «Договор» сейчас - вид выданного документа (`IssuedDocument.kind="contract"`) + текстовое `Order.contract_number` | Пункт 5 требует тонкого реестра договоров |

## 2. Подробно по пунктам

### 2.1 Интеграция счетов в карточку заказа

**Сейчас.** `Invoice` имеет `order`, `trip`, `client`, `carrier`, `direction` (выставленный клиенту / полученный
от перевозчика). Во вкладке «Финансы» заказа стоит `OrderInvoicesBlock` (список счетов заказа, «Выставить счёт»
ведёт на `/finance/invoices/new?order=ID`).

**Предложение (только интерфейс и чтение).**
- Отдельная вкладка «Счета» заказа (видна при `finance.view` и модуле `finance`) с двумя группами: выставленные
  клиенту и полученные от перевозчика; в строке - номер, дата, срок, сумма, остаток, статус, переход в счёт.
- Сводка над списком: выставлено / оплачено / остаток (берётся из тех же полей счетов - **без нового расчёта**,
  суммы приходят с сервера).
- Действия: «Выставить счёт» (существующая форма `InvoiceFormPage` с `?order=`), «Печать» и «Скачать»
  (существующие виды документов `invoice_print`/`act`), «Платёж» (существующий `PaymentDialog`).
- В `OrderInvoicesBlock` во вкладке «Финансы» остаётся компактная ссылка «Все счета» (совместимость).

**Backend.** Изменений нет: используется `GET /api/finance/invoices/?order=ID`. Если понадобится агрегат по заказу -
одно read-only поле в уже существующем сериализаторе счёта, без хранения.

**Финансовые гарантии.** Новых сущностей нет; правила выставления счёта, НДС, валютные снимки, закрытие периодов
не затрагиваются. Тесты: интерфейсные (права, модуль, пустое состояние) + существующие финансовые тесты без изменений.

**Риск.** Низкий. Главное - не продублировать «Остаток» вычислением на клиенте.

### 2.2 Кредитные лимиты и «Работа разрешена»

**Сейчас.**
- `Client.credit_limit` и проверка в `finance/invoices.py`: если долг клиента в тенге + новый счёт > лимита -
  `FinanceError("credit_limit_exceeded")`; переопределить можно с правом и причиной, факт пишется в аудит.
- Отчёт «Долги» отдаёт `credit_limit` и `limit_usage_pct`.
- У клиента и перевозчика есть `status` (активен/неактивен). Для **перевозчика правило уже есть**: рейс принимает только
  активного (`trips/services._carrier`, ошибка «Нужен активный перевозчик этой компании»). Для **клиента правила нет**:
  `ClientField` заказа берёт любого неудалённого клиента, поиск в форме заказа неактивных не скрывает.

**Предложение.**
1. *Показ.* В карточке клиента (вкладка «Основное») и в шапке - индикатор «Использовано N % лимита»
   (данные из существующего отчёта долгов, один запрос). Предупреждение при создании заказа и счёта: «до лимита осталось X».
2. *«Работа разрешена».* Не вводить новое поле: определить правило поверх существующего `status`:
   `inactive` = работа запрещена. Для перевозчика оно уже действует в рейсах; **новое - только для клиента**: серверная
   проверка при создании заказа (код ошибки `party_inactive`), переопределение - право `orders.override_party_block`
   с причиной в аудит. В интерфейсе - скрывать неактивных в выборе клиента и объяснять причину отказа.
   Это **новая проверка**, а не изменение расчётов; финансовые операции по уже созданным записям не блокируются.
3. *Журнал.* Изменение лимита и статуса уже попадает в аудит (`PartyBase` через `AuditedMixin`) и видно во вкладке «История».

**Решение владельца.** Нужен ли запрет на *создание заказа* неактивному клиенту, или достаточно предупреждения.
Рекомендую предупреждение + запрет с правом переопределения: так нет тупиков в работе.

**Риск.** Средний: затрагивает сценарий создания заказа. Закрывается тестами «неактивный клиент / с переопределением /
без права», старые сценарии (активный клиент) не меняются.

### 2.3 Метки заказов и рейсов

**Сейчас.** Сущности меток нет.

**Предложение (минимальная модель, без дублей).**
- `Label` (`TenantModel`, мягкое удаление): `name`, `color` (из фиксированной палитры токенов), `scope`
  (`order` / `trip` / оба), уникальность `(company, name)`.
- Связи `OrderLabel(order, label)` и `TripLabel(trip, label)` (через-таблицы), уникальность пары.
  Альтернатива - `ManyToManyField` на `Order`/`Trip`; рекомендую его: меньше кода, аудит снимков полей не затрагивается.
- API: `/api/labels/` (CRUD, права `labels.view/create/update/delete`), поле `labels: [id]` в сериализаторах заказа и рейса,
  фильтр `?label=id` в списках.
- Интерфейс: выбор в карточке заказа/рейса, цветные чипы в списках, фильтр «Метка», управление в
  `Настройки → Справочники` (как обычный справочник - **без отдельной страницы**).
- **Вариант без новой таблицы:** реализовать метки как справочник `Handbook` с кодом `order_label`
  (механизм справочников уже есть: группы, активность, порядок) + M2M на значения. Это проще и согласовано с
  существующей архитектурой; цвет хранится как `code` значения. Рекомендую этот вариант.

**Миграции.** Одна на справочник и поле; RLS не нужен для M2M-таблицы, если она содержит `company_id` через FK (проверить
`check_rls`: through-таблица должна быть `TenantModel`, иначе добавить `company` и RLS).

**Риск.** Низкий. Не влияет на финансы.

### 2.4 Почта (со всем функционалом)

**Сейчас.** Отправки почты нет: ни настроек SMTP, ни модели письма. Приглашения и пароли выдаются одноразовыми ссылками вручную.

Состав функций «как у TransPro» и честная оценка:

| Функция | Что нужно | Бесплатно на нашей инфраструктуре? |
|---|---|---|
| Написать письмо (получатели, тема, текст) | Модель `Message`, форма, отправка | Да, если есть SMTP-ящик клиента |
| Письмо из записи (заказ, рейс, клиент, счёт) | Привязка `order/trip/client/invoice` (как у `IssuedDocument`) | Да |
| Вложения - выданные документы | Ссылка на `IssuedDocument` + генерация файла (уже есть, DOCX; PDF только где есть конвертер) | Да (DOCX); PDF - ограничение Vercel |
| Шаблоны писем с подстановками | Использует движок подстановок документов | Да |
| Статусы: черновик, в очереди, отправлено, ошибка | `Message.state` + журнал попыток | Да |
| Папки «Исходящие / Черновики» | Фильтры по `state` | Да |
| **Входящая почта** (IMAP) | Постоянный воркер, опрос ящика | **Нет**: на бесплатном Vercel нет постоянных процессов; нужна отдельная инфраструктура |
| Фоновая отправка и повторы | Очередь + воркер | Ограниченно: Vercel Cron на бесплатном плане редкий; Redis/Celery не предусмотрены |

**Предложение - поэтапно.**

*M1. Исходящая почта (без инфраструктуры).*
- Настройки компании: SMTP-сервер, порт, шифрование, логин, пароль, адрес отправителя, имя.
  **Пароль хранится зашифрованным** (ключ шифрования - в переменной окружения; в БД и в API не отдаётся, только «задан/не задан»).
  Ящик подключает сама компания (её почтовый сервис); мы не покупаем и не подключаем платный сервис.
- Модели: `MailAccount` (на компанию), `MailTemplate`, `MailMessage` (тема, тело, получатели, состояние, ошибка, привязки
  `order/trip/client/invoice`, `sent_at`, `created_by`), `MailAttachment` (ссылка на `IssuedDocument` либо файл).
- Отправка: синхронная в запросе с коротким таймаутом (30 с лимит функции) и записью результата; при ошибке письмо остаётся
  в «Ошибка» с кнопкой «Повторить». Ограничение скорости на пользователя и компанию (защита от рассылки спама).
- Интерфейс: раздел «Почта» (список: Тема / Кому / Состояние / Отправлено / Связано с; окно «Написать»), вкладка
  «Письма» в карточках заказа, клиента, рейса, кнопка «Отправить по почте» на выданном документе.
- Права: `mail.view`, `mail.send`, `mail.manage_account`. Модуль `mail` в `module_catalog` (включается тарифом).

*M2. Входящая почта* - **не предлагается к реализации без отдельного решения**: требует воркера и хранилища вложений,
то есть инфраструктуры, а также юридически чувствительна (хранение переписки). Если понадобится - варианты:
(а) только «Ответить из системы» и пересылка вложений по ссылке; (б) отдельный бесплатный воркер на свободной
платформе - оценить на момент решения, условия бесплатных тарифов меняются.

**Безопасность и персональные данные.** Получатели и тексты - персональные данные: доступ по RLS и праву, запись в аудит
факта отправки (без текста), запрет отправки вложений без права на документ. Защита от инъекции заголовков, лимит
размера вложений, проверка адресов. Шифрование пароля SMTP (ключ отдельно от `DJANGO_SECRET_KEY`).

**Решения владельца.** (1) Подходит ли модель «ящик подключает сама компания» (без нашего почтового сервиса).
(2) Нужна ли входящая почта сейчас (рекомендую нет). (3) Включать ли PDF-вложения (ограничение конвертера).

**Риск.** Высокий по объёму и безопасности; делать после пунктов 1-3, 5-9.

### 2.5 Договоры с привязкой к заказу и рейсу

**Сейчас.** «Договор» - вид выданного документа (`IssuedDocument.kind="contract"`, нумерация, шаблон, снимок данных,
связь с клиентом). В заказе - текстовое `contract_number`. Связи «договор ↔ заказ/рейс» как сущности нет.

**Предложение - тонкий реестр поверх выданных документов.**
- `Contract` (`TenantModel`, мягкое удаление): `party_type` (`client`/`carrier`), `client`/`carrier` FK (ровно один),
  `number`, `date`, `valid_until` (пусто - бессрочно), `kind` (из справочника «Виды договоров»), `title`, `comment`,
  `document` (необязательная ссылка на `IssuedDocument` - сам файл по шаблону), `created_by`.
- `Order.contract` и `Trip.contract` - необязательные FK. **Текстовое `Order.contract_number` остаётся** (совместимость);
  при выборе договора номер подставляется, старые заказы не меняются. Миграция данных - необязательная и обратимая:
  создать договоры из уникальных `contract_number` по клиенту с пометкой «импорт».
- API: `/api/contracts/` (фильтры по клиенту/перевозчику, действующие), вкладка «Договоры» в карточках клиента и перевозчика
  (сейчас там «Документы»), выбор договора в форме заказа и рейса (из договоров этого контрагента).
- Правило: нельзя выбрать истёкший договор без подтверждения (предупреждение, не запрет). Удаление договора, на который
  ссылаются заказы/рейсы, запрещено (как для контактов: `contact_in_use`).
- Документы: договор-заявка и счета подставляют номер и дату выбранного договора (через существующий контекст документа).

**Финансы.** Договор не хранит сумм. Отсрочка платежа остаётся там, где есть (заказ/клиент).

**Риск.** Средний: затрагивает формы заказа и рейса. Закрывается совместимостью (поле необязательное) и тестами форм.

### 2.6 Редактор справочников в интерфейсе

**Сейчас.** Страница есть и работает: группы слева, значения справа, добавление, правка, активность, удаление, статусы
(начальный/конечный) с предупреждением, права `handbooks.view/create/update/delete`. Набор самих справочников фиксирован
(создаётся сидингом, через API не создаётся - так задумано, на нём держатся статусы и расчёты).

**Разрыв с TransPro - косметический и вспомогательный:**
- счётчик значений и описание у каждого справочника (описание - в `Handbook`, нужна одна миграция и текст в `defaults.py`);
- перетаскивание порядка значений (сейчас - числом);
- видимое «Используется» (число записей, где значение применено - в `HandbookUsage` уже есть), запрет удаления с
  понятным объяснением вместо ошибки сервера;
- перенос на новый шаблон страницы (дизайн-система) - частично сделан в этапе 1.

**Предложение.** Малый объём: интерфейс + одно read-only поле `usage_count`. **Создание новых справочников пользователем
не предлагается** - это сломало бы системные коды (`COMPLETED`, `PLANNED` и т.д.). Единственное исключение - справочник меток (п. 2.3).

**Риск.** Низкий.

### 2.7 Аудиты входов

**Сейчас.** В модели аудита есть действие `login`, функция `log_login()` и `/api/audit/` с фильтрами (`action`, `user`,
даты). Но `log_login()` **нигде не вызывается**, поэтому записей входа нет; страницы журнала в интерфейсе тоже нет
(есть только чтение через `EntityHistory` в карточках).

**Предложение.**
- *Запись.* Вызвать `log_login` после успешного входа (после проверки TOTP, если он нужен), в `changes` - способ
  (пароль / одноразовая ссылка / смена контекста), без секретов. Неуспешные попытки - отдельное действие
  `login_failed` (логин-идентификатор хэшируется или усекается, чтобы журнал не раскрывал чужие учётные записи; причина -
  общий код, не «нет такого пользователя»). Лимиты и блокировки уже есть - журнал не должен их ослаблять
  (запись неуспешных попыток ограничивается тем же throttle, чтобы журнал нельзя было переполнить).
- *Просмотр.* Страница «Настройки → Аудит входов»: таблица (время, пользователь, событие, IP, устройство/агент),
  фильтры (пользователь, событие, период). Право: `audit.view` (сейчас чтение журнала привязано к `company.view` - разделить).
- *Сроки хранения.* Политика очистки (например, 12 месяцев) командой управления; персональные данные (IP) - в
  описание политики конфиденциальности.
- *Платформенный уровень.* Входы владельца платформы пишутся в платформенную историю (`/platform/history`) - отдельно.

**Риск.** Средний: затрагивает поток входа (критичный для безопасности). Нужны тесты на то, что запись журнала не
ломает вход при ошибке записи (запись «по возможности», вход не блокируется) и не пишет секреты.

### 2.8 Реквизиты и банковские счета контрагентов

**Сейчас.** У клиента и перевозчика - **одна** пара `bank` + `iban` (и адрес). У нашей стороны - `LegalEntity`
(так же одна пара банк/IBAN).

**Предложение.**
- `BankAccount` (`TenantModel`, мягкое удаление): владелец - клиент, перевозчик или наше юрлицо (ровно один FK),
  `bank`, `bic`, `iban`, `currency`, `kbe`, `knp` (для платёжного поручения в РК), `is_default`, `note`.
  Уникальность `(owner, iban)`.
- Существующие `bank`/`iban` **остаются** для совместимости; миграция данных создаёт по счёту с `is_default` из заполненных
  пар, поля пока не удаляются (чтение - счёт по умолчанию, запись - в обе стороны на переходный период).
- Интерфейс: вкладка «Реквизиты» карточки клиента/перевозчика и юрлица - список счетов, «Добавить счёт», счёт по умолчанию.
- Документы: подстановка реквизитов выбирает счёт по валюте документа (иначе - по умолчанию). Предупреждение
  «Счёт напечатается неполным» (как у TransPro) - если не заполнены БИК/Кбе.
- Аудит: значения IBAN маскируются так же, как сейчас (`audit_masked_fields`).

**Финансы.** Банковский счёт - справочные данные для печати, не ledger-сущность; платежей и остатков не хранит.

**Риск.** Средний: миграция данных и подстановка в документы. Закрывается обратимой миграцией и тестами документов.

### 2.9 Комментарии и история на сущностях везде

**История.** Работает уже сейчас: `EntityHistory` (этап 2) читает журнал аудита для заказа, рейса, клиента,
перевозчика. Нужно подключить к остальным сущностям (техника, водитель, счёт, документ, пользователь) - по строке
на страницу, backend уже пишет аудит (проверить покрытие каждой модели и добавить `AuditedMixin` там, где его нет).
Разделить право чтения истории от `company.view` (`audit.view`, см. п. 2.7), чтобы менеджер видел историю своих записей.

**Комментарии.** Хранилища нет; компонент `EntityComments` готов и не подключён.
- `Comment` (`TenantModel`, мягкое удаление): `subject_type` + `subject_id` (тот же приём, что у `IssuedDocument`:
  `"forwarding.order"`), `body`, `author`, `created_at`, `edited_at`. Упоминания и вложения - не в первом шаге.
- API: `GET/POST /api/comments/?subject_type=&subject_id=`, `PATCH/DELETE` - только автору (или праву `comments.moderate`).
- Права: чтение - то же, что и чтение самой записи (проверка по `subject_type`); создание - `comments.create`.
- Подключение: вкладка «Комментарии» в заказе, рейсе, клиенте, перевозчике (компонент уже сделан).
- Уведомления об упоминаниях и мессенджер - **не включены** (отдельное решение, мессенджер исключён).

**Риск.** Средний: правило «кто видит комментарии» должно идти за правом на запись-владельца, а не быть отдельным обходом.

## 3. Сквозные требования

- **Права.** Каждое новое право добавляется в каталог (`permissions_catalog.py`, `features/settings/roles/catalog.ts`) и
  выдаётся системным ролям по умолчанию осознанно; UI только прячет, сервер проверяет всегда.
- **RLS и миграции.** Новые таблицы - `TenantModel` + `enable_rls`; перед релизом `manage.py check_rls` под ролью приложения.
  Миграции добавляющие, обратимые; данные не удаляются; прежние поля остаются до отдельного решения.
- **Тарифы и модули.** Почта - отдельный модуль (`mail`); метки, договоры, комментарии - в базовых модулях.
- **Финансы.** Ни один пункт не добавляет сумм, ставок, проводок, статусов оплаты. Любой экран, показывающий деньги,
  читает их из существующих API `finance`. Тесты финансов (включая `test_legacy_carrier_cost`) остаются неизменными.
- **Совместимость.** Старые адреса и поля (`?open=`, `contract_number`, `bank`/`iban`) работают; новые поля необязательны.
- **Язык и доступность.** Все строки - в `ru.json`/`kk.json`; интерфейс на компонентах дизайн-системы этапа 1.
- **Тесты.** По пункту: backend (права, RLS-изоляция между компаниями, граничные случаи) + frontend (права, пустые и
  ошибочные состояния). Полный backend-прогон - в CI.

## 4. Рекомендуемый порядок

1. **Малые и безопасные:** 2.1 счета во вкладке, 2.6 справочники, 2.9 история на остальных сущностях.
2. **Основа для остального:** 2.7 аудит входов (+ `audit.view`) - даёт разделение прав, нужное 2.9 и 2.4.
3. **Данные контрагентов:** 2.8 реквизиты, 2.5 договоры (зависят друг от друга косвенно через подстановку в документы).
4. **Логика допуска:** 2.2 лимиты и «Работа разрешена».
5. **Организация работы:** 2.3 метки, 2.9 комментарии.
6. **Почта (M1):** последней - самый большой объём и вопрос инфраструктуры.

Зависимости: 2.9 (комментарии) и 2.4 используют `audit.view` и привязку к записям из 2.5; 2.5 использует 2.8 при печати.

## 5. Что требует решения владельца

1. Запрет создания заказа неактивному клиенту (рекомендуется предупреждение + запрет с правом переопределения).
2. Почта: подходит ли «ящик подключает сама компания», нужна ли входящая почта, нужны ли PDF-вложения.
3. Срок хранения журнала входов и политика по IP-адресам.
4. Метки как справочник (рекомендуется) или отдельная сущность.
5. Судьба старых полей (`contract_number`, `bank`, `iban`) - оставить навсегда или убрать отдельным этапом после перехода.

## 6. Не входит

Мессенджер, база знаний, платные интеграции (почтовые, платёжные, СМС), входящая почта без отдельного решения,
любые изменения финансового движка и расчётов, включение `engine=new`.
