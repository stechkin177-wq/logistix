# Первичное создание аккаунта владельца и своей компании (один аккаунт)

Статус: механизм готов и проверен тестами; **в production ничего не создавалось**, реальные данные не
использовались. Выполнять только с отдельного разрешения заказчика (деплой и создание аккаунтов).

## 1. Поддерживает ли архитектура один аккаунт на оба уровня: да, безопасно

Один пользователь может одновременно иметь платформенную роль `owner` и членство «Администратор» в своей
компании. Это проверено тестом `test_single_account_is_platform_owner_and_company_admin_with_independent_contexts`.
Второй аккаунт не нужен. Права, токены и контексты остаются независимыми:

| Свойство | Как обеспечено |
|---|---|
| Роль платформы не зависит от компании | `User.platform_role` проверяется по БД на каждом запросе; членство в компании и `is_superuser`/`is_staff` платформенных прав не дают |
| Токен платформы не открывает данные компаний | токен `ctx=platform` без `company_id`: любой эндпоинт компании отвечает 403 `company_context_required` |
| Токен компании не открывает платформу | токен `ctx=company`: платформенные API отвечают 403 `platform_context_required` |
| Права внутри компании ограничены ролью | в контексте компании действуют только права роли «Администратор» и состояние подписки компании; платформенная роль в компании ничего не добавляет |
| Вход | пароль, затем TOTP; пока код не подтверждён, токенов нет (есть только короткий подписанный талон, он API не открывает) |
| Из компании в платформу | только со **свежим кодом TOTP** (токен компании сам по себе платформу не открывает: кража сессии компании не даёт платформенных прав) |
| Из платформы в компанию | без повторного кода; членство и подписка проверяются, данные контекстов не смешиваются (кэш интерфейса очищается) |
| Выход и смена пароля | отзывают все выданные токены этого аккаунта на всех устройствах |
| Журнал платформы | пишутся вход, неудачный пароль/код, подключение TOTP, смены контекста, установка пароля |

Остаточный риск единственного аккаунта: тот, кто знает ваш пароль **и** контролирует ваш аутентификатор,
получает оба уровня; для двух отдельных аккаунтов нужно было бы скомпрометировать оба. Он ограничен тем, что
второй фактор обязателен и запрашивается заново при каждом переходе в платформу.

## 2. Какие данные потребуются от вас

Секретов передавать не нужно. Нужно только (всё перечисленное не секретно):

1. **Адрес входа (e-mail) для аккаунта владельца** - отдельный личный адрес, не общий ящик. Он же логин и в
   платформе, и в компании. (Почту система не отправляет: адрес нужен только как логин.)
2. **Имя и фамилия** для отображения.
3. **Название вашей транспортной компании** (как в интерфейсе) и **профиль деятельности** из списка
   (`carrier`, `forwarder` и др.; список выводит Центр управления/`/api/activity-profiles/`). Состав модулей затем
   правится вручную.
4. **Адрес приложения** (`https://...`), когда будет выбрана площадка, - он нужен для одноразовой ссылки.
5. Установленное на телефоне приложение-аутентификатор (Google Authenticator, Aegis, FreeOTP или аналог).

**Не нужны и не передаются:** пароль, ключ TOTP, документы, телефон. БИН, юридическое название и прочие
реквизиты компании вы внесёте сами после входа в «Настройки → Компания» и в справочники.

## 3. Безопасный порядок (пароль никто не видит и не передаёт)

1. Вы присылаете данные из раздела 2 (любым каналом: они не секретны).
2. **Администратор сервера** (с вашего разрешения, на целевом окружении после выкладки) выполняет:
   ```bash
   # 1) аккаунт владельца БЕЗ пароля + одноразовая ссылка (печатается в терминале администратора)
   ./deploy/dc.sh exec backend python manage.py create_platform_owner you@example.com \
     --full-name "Имя Фамилия" --base-url https://<адрес-приложения>

   # 2) ваша компания: тот же аккаунт становится её администратором, пароль не нужен
   ./deploy/dc.sh exec backend python manage.py bootstrap_company \
     --name "Название компании" --owner-login you@example.com --allow-existing-user \
     --profile <код-профиля>
   ```
   Ссылка действует около 2 часов (`PASSWORD_SETUP_TIMEOUT_SECONDS`), работает **один раз** и перестаёт работать,
   как только пароль задан. Выдавайте её, когда вы готовы открыть её сразу.
3. Ссылка передаётся вам **личным закрытым каналом** (не в групповом чате, не по почте общего ящика). Открываете
   ссылку и сами выбираете пароль (длинный, уникальный, из менеджера паролей). Администратор сервера пароля не видит.
4. Первый вход (`/login`): e-mail и пароль -> экран подключения TOTP. Вы сами добавляете показанный ключ в
   приложение-аутентификатор (вручную или по otpauth-ссылке) и вводите код. Первый верный код включает TOTP.
   Дальше каждый вход - пароль и код.
5. Вы попадаете в Центр управления (`/platform`). Кнопка «Открыть компанию…» ведёт в вашу компанию с правами
   администратора, «Центр управления» в меню компании возвращает в платформу (с кодом).
6. **Проверка, что ссылку не перехватили:** если при открытии ссылка уже «недействительна» - её использовал кто-то другой
   или она истекла; сообщите администратору сервера: он выпустит новую (`issue_password_link`), а журнал платформы
   покажет, кто и когда задал пароль и подключил TOTP (`password_set`, `totp_enabled`). После первого входа сверьте эти
   записи со своими действиями.
7. Сразу после первичной настройки: резервная копия (раздел 8 RUNBOOK) и проверка, что вход без кода невозможен.

Если пароль забыт или потерян телефон: `issue_password_link <e-mail> --base-url ...` и `reset_totp <e-mail>`
(раздел 13 RUNBOOK); оба действия отзывают прежние токены.

## 4. Что не делается

Публичной регистрации владельца нет; второго аккаунта и параллельного механизма авторизации нет;
`is_superuser` не назначается; `engine=new` не включается; реальные данные в репозитории и тестах не используются.
